Aitta packages: an app packed, signed and installed
===================================================
A release is two files, the archive
and its signature; it is installed from them, from the command line or
from an Aitta registry through the client.

The manifest
------------
An app's meta.json, at the app directory's root (apps/<app>/meta.json):

    {
        "author": "celeron55",        a-z, 0-9 and _, 1 to 40
        "name": "demo_digger",        the same
        "version": "1.0.0",           letters, digits, . - + _, 1 to 40
        "engine_api": 2,              the engine API it is written for
        "license_code": "Apache-2.0",
        "license_media": "CC-BY-SA-4.0",
        "description": "Dig down.",   300 characters at most
        "home_hearth": "https://forum.buildat.org",   optional: where
                                      its feedback and news go
        "changelog": "CHANGELOG.md",  optional: a file in the archive
        "kind": "app",                optional: "app" or "extension"
        "audience": "everyone",       optional: "everyone", "teen" or
                                      "adult"; Aitta's page at / lists
                                      only "everyone" and "teen"
        "serverless": true,           optional: its client half runs
                                      with no server (Play)
        "icon": "icon.png",           optional: a square PNG in the
                                      archive, 256 px and 64 kB at most
        "screenshot": "shot.jpg",     optional: a PNG or a JPEG
                                      (baseline or progressive, 8-bit),
                                      1920 px a side and 2 MB at most
        "base": "vanilla",            optional: the app this one is a
                                      variant of (doc/luanti_apps.txt):
                                      a shipped app's name, or
                                      "<author>.<name>" of an installed
                                      package
        "base_version": "1.2.0",      optional, with an <author>.<name>
                                      base: the lowest version taken;
                                      the newest installed of its major
                                      version is used
        "needs": {"memory_mb": 1024, "mesh_threads": 2}
                                      optional: what its web client needs
                                      at least (buildat.resources(),
                                      doc/client_api.txt); the play page
                                      says so plainly when the browser
                                      gives less, and offers to start
                                      anyway
    }

license_code and license_media are SPDX ids, or an expression of them
joined by AND and OR with parentheses ("MIT AND (CC-BY-SA-4.0 OR
LGPL-2.1-or-later)"); an Aitta takes it when every id in it is on its
list. A base that does not resolve refuses the install in the client
("install it first").

The icon and screenshot are checked by their bytes, not their names, at
pack and again at publish. The icon is on the release's launch grid
tile, its row in "Apps from Aitta" and Aitta's pages; the screenshot in
the row's panel and on the package page.

Client-side Lua (a client_lua directory's, an extension's every file)
runs on LuaJIT natively and on Lua 5.1 on the web. Aitta parses it at
publish with luac51 (installed beside the server) and scans it for
LuaJIT's \x, \z and \u{ escapes: a "serverless" release that does not
load is refused, another is listed with the problems as a warning
(file:line each; the publishers print it).

A release can run in the browser with its server in the page
([WEB_LOCAL_AITTA]) when it is an app, not a variant, whose client Lua
loads on the web, each of whose modules is a .wasm on the server side
("server_wasm") or has no server side ("disable_cpp") -- or is C++ on an
Aitta with a kit, below -- and whose dependencies are its own modules or
builtins that keep to the web API. Aitta builds such a release's .wasm itself after it is listed, one
release at a time, taking the authors in turn (round-robin; an author's
own in the order published), from the release's source (a release
carries no .wasm); a publish while 3 of the author's releases wait to be
built is refused: `buildat_server --build-wasm`, as the server builds them (cargo
or clang to wasm32), in a box of the build's own (Linux: Landlock and
seccomp) that reads the system's programs and libraries, the toolchain
and the engine's headers and crates, writes its own directory, opens no
socket and gets no environment of Aitta's; 300 s, 600 s of CPU and 2 GiB
of address space a process, 64 processes and threads at once (counted in
the build's user namespace; a kernel before 5.14 counts the uid's across
the host), two compiles at once, its directory at most 3 GiB and 200000
files (measured each second; past either the build ends), and all its
processes together at most BUILDAT_BUILD_MEMORY_MIB of memory (4096 by
default). Every process the build starts ends
with it: the build runs in a PID namespace of its own (an unprivileged
user namespace); where the host allows none, nothing is built. A crate's dependencies are path ones
(no network).

The build's memory total is held by a cgroup of its own where Aitta's
cgroup is delegated to it and Aitta is alone in it: Aitta then moves
itself to <cgroup>/server and makes <cgroup>/build (memory.max the
total, no swap, pids.max 64, one OOM ending the whole build). Elsewhere
Aitta's log says "the build's memory: ... measured every 0.1 s": the
build's own first process sums its processes' memory and ends the build
past the total, which lags (what the build touches in 0.1 s goes past it)
and does not count kernel memory. On the real host, run Aitta as a
systemd service with delegation, which also caps Aitta and its builds
together:

    [Service]
    ExecStart=/opt/buildat/bin/buildat_server -m /opt/buildat/apps/aitta -D /var/lib/aitta
    Environment=BUILDAT_BUILD_MEMORY_MIB=4096
    Delegate=memory pids
    MemoryMax=8G
    MemorySwapMax=0
    TasksMax=1024

ExecStart must start buildat_server itself (no shell around it): with
another process in its cgroup Aitta makes no cgroup for the build. Aitta
says "A build's cgroup: ..." at its start when it made one. Built, the release says "web": true and names each .wasm
in "web_wasm" ({"<module>.server.wasm" or "<module>.wasm": its sha256});
a failed build leaves it out of the page, Aitta's log saying why. An
Aitta not on Linux builds none.

C++ modules ([WEB_LOCAL_AITTA_CPP]) are built for the page only by an
Aitta started with BUILDAT_AITTA_CPP_KIT naming a kit: the engine's
server for packages (web/local/_aitta) as parts -- its objects,
libraries, flags, headers and packed files, the .js and .wasm it made,
and the emsdk version it was made with -- which util/build_web_server.sh
"$PWD/src/server/web/_aitta" makes in Build-webserver/aitta_kit. The
kit builds with the emsdk at $EMSDK, else ~/emsdk, on the Aitta host
([AITTA_KIT_IN_RELEASE]), which must be the version it was made with:
3.1.60 (util/docker/linux's EMSDK_VERSION), installed as

    git clone https://github.com/emscripten-core/emsdk.git ~/emsdk
    cd ~/emsdk && ./emsdk install 3.1.60 && ./emsdk activate 3.1.60

Another version links a .js that is not the kit's: Aitta says at its
start "the kit at ... needs emsdk 3.1.60, and the emsdk at ... is ..."
and refuses C++ for the page until it is fixed. The build reads the
emsdk's cache and cannot write to it; an emsdk installed as above has
what it reads. In the same build, in the same box, the kit's fixed script
(util/aitta_cpp_build.py) compiles each C++ module (<name>_web.cpp or
<name>.cpp, and its wasm/'s C and C++) with the kit's flags and none of
the module's own -- a module with "cxxflags" is not for the page -- and
links them with the kit's objects into a server of the release's own.
Aitta then checks the output, not the source: the .wasm (at most 32 MiB)
imports nothing the kit's does not, each of the same type, and has no
custom section the kit's has not; its .js is the kit's but for where the
EM_ASM code is (moved by one amount, the release's own data before it).
So EM_ASM, EM_JS, emscripten_run_script and any library function the
engine does not use are refused, whatever macro wrote them. Built, the
release says "web_cpp": true (not "web": a client before this would run
it without its C++) and "web_server": {wasm (its sha256), js (the kit's
.js's sha256), shift}. The page never runs the release's .js: it runs
the .wasm with its own web/local/_aitta/buildat_server.js, so the .wasm
reaches what that .js's imports reach and no more; the check refuses
early what could not run so. A kit of another engine version links every
such release again at Aitta's start; until then the page of the new
version runs none of them.

A package of kind "extension" is a client extension: init.lua at its
root, run in the client's sandbox like extensions/ (an app's client Lua
requires it, or a launch_ui.txt beside it makes it a launch UI, always
sandboxed). The client names it "<author>__<name>", so neither part may
have "__" in it or start or end with _. It has no saves to pin, so an
installed version replaces the one before it. An author/name stays the
kind it was first installed as.

engine_api is the engine API it is written for; the engine runs
interface::aitta::ENGINE_API_MIN...ENGINE_API (src/interface/aitta.h,
2...2 for 0.7) and bumps it when a change breaks apps. A release outside
the running engine's range is not packed or installed, and the client's
list says it is "not for this Buildat"; an Aitta keeps releases of every
engine API. Publishing keeps the package's own engine_api: its author
bumps it, in meta.json and in its modules', when porting it.

The commands
------------
    bin/buildat aitta keygen <key file>
        A new author key. Prints its public half. The file is the secret:
        whoever has it publishes as you. It is never overwritten.

    bin/buildat aitta pack <app dir> <key file> <out dir>
        Writes <author>-<name>-<version>.zip, the app directory (names
        starting with '.' and aitta_page/ left out), and .sig beside it: the zip's
        sha256, the public key and its signature over the hash.

    bin/buildat aitta install <release .zip> <user path>
        Checks the hash, the signature and the manifest, and unpacks into
        <user>/installed/<author>/<name>/<version>/. The first version
        installed keeps its key in <user>/installed/<author>/<name>/key; a
        later version signed by another key is refused. A version already
        there is not replaced: an update is a new directory beside it.

    bin/buildat aitta install <Aitta> <author>/<name>[@<version>] <user path>
        The same, fetched from an Aitta's list by name: the version asked,
        else the newest listed. A version not listed is refused with the
        versions there are; one installed already is only said. Prints the
        version's directory.

    bin/buildat aitta publish <release .zip> <Aitta's host:port>
        Uploads a release to an Aitta (apps/aitta). Its key has to be bound
        to its author name there first.

    bin/buildat aitta page <Aitta's host:port> <author>/<name> <dir> <key file>
        Sends the package's page (below): <dir>'s description.txt and its
        PNG and JPEG screenshots, in the order of their names, packed as
        <dir>/.packed/<author>-<name>-page.zip and .sig (format
        "aitta-page-1", so a release's signature is never a page's).

Publishing from the client
--------------------------
Settings, Developer, "Publish an app or extension" (not on the web
client) does the commands above without a terminal:
  - Packages are directories in <user>/dev_apps/<name>; "New app..." and
    "New extension..." write a small one there (an app with client Lua
    only), and "Open folder" opens it. A dev app is a "Dev" tile on the
    launch grid ("dev:<name>"; its server and saves know it as <name>);
    a dev extension is loaded over an installed one of the same name.
  - The manifest form edits meta.json, each field checked as it is typed,
    the reason under it.
  - "Create my publishing key" writes <user>/aitta_keys/<author>.key.
    "Bind on <Aitta>..." joins the Aitta with the author name and public
    key filled in its Bind form (the Aitta's account signs in there);
    "Back to the launcher" returns. The screen asks the Aitta's
    GET /api/v1/aitta/info?key=<public key> ({ok, licences, author}) whether
    the key is bound.
  - "Pack and publish" packs into <user>/aitta_releases and uploads. A
    version already published is refused with "Raise the version", which
    raises the last number of the version and saves it; "Pack and
    publish" again publishes that.
  - "The page on <Aitta>..." edits the package's page: the description
    in a text box, the screenshots from the package's aitta_page/
    ("Show the folder"); "Send" writes aitta_page/description.txt and
    sends it as `aitta page` does.
util/aitta_publish_check.sh drives all of it; util/package_media_check.sh
the page.

The package's page [AITTA_PACKAGE_PAGE]
---------------------------------------
Set by the publisher on an Aitta, not in any release: the same whichever
release is shown, and not sent to a client. A description (plain text,
20000 characters at most; a blank line a paragraph, a line break kept,
an http(s):// address a link, nofollow) and up to 8 screenshots, each as
the manifest's screenshot. Signed by a key bound to the package's
author, with a time newer than the page there, which it replaces whole;
a package with no release on the Aitta has none. /p/<author>/<name>
shows, in order: the heading with the icon, the short description, the
release's screenshot and the page's (thumbnails linking the images), the
page's description, the releases, Install and Report. The page is
reportable ("The page" in the Report form; its id is <author>/<name>); a
moderator delists it, or bars its author, and the releases stay. After a
moderator's delist the next page sent waits, hidden, with a report of
its own in the queue: dismissing it shows the page.

Aitta, the registry
-------------------
apps/aitta is a buildat app. An author joins it (its accounts: a local
account, or a Starport ID where its admin set that up), and binds an
author name to the public key keygen printed; the name and the key do
not change after. A published release is checked -- the signature by a
bound key, the hash, the manifest, its author being the key's, the
licences against the instance's list (free ones by default, in its
settings), the size -- and listed, unreviewed. The admin can delist and relist, in the moderators'
audit log and told to the owner as a moderator's delist is; a delist
({"cmd": "delist", "release": "<author>/<name>/<version>", "reason": ...,
"text": ...}) takes one of the report reasons, and the list's "delisted"
says it as its "why" ("malware: <text>"), which a server following the
Aitta reads (util/serve_latest_release.sh).
A package's later release is listed once it is the settings'
"update_delay" seconds old (0 by default), so a release made with a
stolen key can be reported and delisted before clients are offered it.
The page at / is for a browser that may be anyone's: it lists a release
only once it is "page_delay" seconds old (3600 by default), and only one
whose audience is "everyone" or "teen". The admin changes a setting
on Admin > Settings in the client's Server window (each as JSON, with
what it does), or with the app's request {"cmd": "set_settings",
"settings": {...}}; {"cmd": "settings"} answers them all.

The server's moderators and admins are its reviewers: "Review releases"
on Aitta's page lists the releases to review, oldest first; a release's
page has its meta, its files (each viewable as text), a diff against the
package's last reviewed release, a checklist, and Reviewed, Needs
changes (the note to the author), Relabel (the audience; the author
cannot set it back without a review) and Delist, each in the audit log
with whether the reviewer playtested it. Playtest makes a ticket (an
hour, one fetch of each file, a release not listed too) and leaves to
the launcher, which asks in its own dialog before it installs the release
under <user>/review/<author>__<name>/<version>, apart from the installed
ones, and starts it: to its server "review.<author>__<name>", saves of
its own. Its tile is badged Playtest, with a "remove" tile beside it.

Anyone reports a release: "Report..." on Aitta's page in the launcher or
on an installed tile, or the form on a package's web page. The reasons
are Starport's and malware, licence and broken. A report weighs the
setting "anon_weight" (0.01) without a key and "key_weight" (0.1) with
the client's report key, more or less by the key's record; one network
counts once in a group (a release and a reason). Past the "thresholds"
({hide, delist} by reason; malware and CSAM 1 and 2) a release is out of
the list until a moderator looks. "Reports" on Aitta's page is the
moderators' queue: dismiss, or unreview, delist the release, delist the
package or bar the author from publishing (days, or until lifted). The
author reads what was done on their Aitta page ("What was done to my
releases") and appeals there, once a statement; another moderator than
the one who acted decides. A delisted release installed in a client is noted on its tile
when the launcher next fetches that Aitta's list.

    GET  /api/v1/aitta/list                   the listed releases, JSON, and
                                              the delisted ones with why;
                                              ?serverless=1 those only
    POST /api/v1/aitta/report                 {release (or <author>/<name>
                                              for its page), reason, text,
                                              key}
    POST /api/v1/aitta/report_status          {key, receipts}: outcomes
    GET  /api/v1/aitta/archive/<sha256>.zip|.sig a listed release's files
    GET  /api/v1/aitta/wasm/<sha256>.wasm     a .wasm built for a listed
                                              release (its "web_wasm" or
                                              "web_server"), with CORP
                                              cross-origin
    GET  /api/v1/aitta/media/<sha256>         a listed release's icon or
                                              screenshot, image/png or
                                              image/jpeg by its bytes, or a
                                              shown page's screenshot
    GET  /api/v1/aitta/info?key=<public key>  {ok, licences, author}: the
                                              author the key is bound to
    GET  /                                    a page of each package's latest
                                              release, for a browser
    GET  /p/<author>/<name>                   a package's listed releases
                                              (the newest, the rest
                                              folded), then Install: "On
                                              the client" and "On a
                                              dedicated server", folded

A refusal is {"ok": false, "code": ..., "error": ...}: code for a program
to match ("refused"; "upgrade_required" for a path without /v1/), error
for a person. A manifest's key this Aitta does not know is kept in the
release's "manifest"; a kind it does not know is listed as "other", which
no client installs, and an audience it does not know as "adult".

Every API answer has Access-Control-Allow-Origin: *, so a play page on
another origin fetches the list and the archives (and the .wasm, from a
cross-origin isolated page). A serverless release, or one whose server
runs in the page, says "runs in the browser" on the pages; with the
setting "play_url"
(e.g. "https://play.buildat.org"; "" by default, no link) its box on /,
and its package page under the heading and first under Install, link
"Play in the browser" to <play_url>/#run=<author>/<name>.
With "app_hosting_provider" (a URL; "" by default, no link) every app's
box and package page link "Host at <domain>" after it, to
<provider>?aitta=<this Aitta's address>&package=<author>/<name>, both
URL-encoded, nofollow: the provider fetches the package and hosts it. An
extension has none.

The HTTP requests are limited per network (an IPv4 /24, an IPv6 /64):
240 reads and 30 uploads a minute. The web client of an Aitta server is
at /app (/play and /index.html work too).

Browsing and installing in the client
-------------------------------------
"Apps from Aitta" on the launch grid lists the Aittas in the Starport
settings (https://aitta.buildat.org by default; the managed file's
"aittas", or "aitta" for one, overrides them), merged, a package a row
with its newest release ([AITTA_PAGE_LAYOUT], laid out as Browse): the
search filters as it is typed, the dropdown by state (All, Installed,
Updates, Not installed), Ctrl+S sorts by name or newest. The selected
package's panel has its version, kind, author, review state, licences,
size, description and changelog, and Install, or Update where another
version of it is installed, Discuss and Report...; Enter or a second
click on its row installs. Escape closes the page. The client fetches
the release and its .sig and checks them itself before installing; the
new version is on the grid at once. Where the
Starport filters hide unreviewed content ("Apps from Aitta (unreviewed)",
under the lock, or the managed file's filters.unreviewed), a package
shows only its newest reviewed release, and one with none is not shown.

On the web there is no server to install onto: the page lists the
serverless releases and those whose server runs in the page, with Play.
Play on one of the second kind installs it into the browser's storage
(its .sig checked as above), fetches each .wasm its Aitta built and
checks it against the list's sha256, keeps them under .web/ in the
release's directory and goes to ?local=<author>.<name>@<version>. That
page (cross-origin isolated) runs the engine's server for packages, the
builtins that keep to the web API built for the browser (web/local/_aitta,
util/build_web_server.sh), in a worker, hands it the installed files and
the .wasm, and the client joins it as it joins an app's own ?local=
server; the modules' .wasm run on the browser's own wasm, checked,
granted and metered as on a native server. The saves are kept in the
browser. A release with C++ ("web_cpp") has its own server .wasm, kept as
.web/server.engine.wasm with .web/server.json: the page runs it with
local/_aitta's .js when that .js is the one its Aitta's kit had (by
sha256; else "built for another version of this page's engine"), the
EM_ASM addresses moved by the release's shift (src/server/web/post.js).
Its saves are an IndexedDB database of their own (/user/apps/<author>.
<name> in the server's files; the rest of /user is memory): its C++
reaches every file of the server, so no other app's saves are mounted.

Running an installed app
------------------------
Every installed version is a tile on the launch grid, "<label> <version>",
and starts a sandboxed server from its directory. To the client it is
"<author>.<name>@<version>"; to its server, and to its save, shared and
cache directories, "<author>.<name>": every version is one app. `buildat -a
installed/<author>.<name>@<version>/<id>` runs its tile on boot.

A save remembers the release that made it (version and sha256, from the
.aitta_sha256 the install leaves in the version's directory), and another
version of the app does not open it. Where two versions of an app are
installed, each has a second tile, "<label> <version>: move saves here",
which plays that version and moves the saves another version made to it
(the launch parameter aitta_move_saves=1).

On a dedicated server [AITTA_SERVE]
-----------------------------------
util/serve_latest_release.sh takes <author>/<name> as a game: it runs the
newest version installed in that server's user directory, as the server
<author>.<name> (its saves under <user>/apps/<author>.<name>/). Install it
first with the command above, or set AITTA=<the Aitta's address>: then
the script installs it, and at each update check installs the newest
listed release, compiles it and restarts onto it as it does for a new
engine release (the same wait for players, the same warning). Without
AITTA the installed version stays until one is installed by hand. A
package's page on the Aitta shows these commands with its name filled in,
under Install's "On a dedicated server", after "On the client" (Apps
from Aitta, this Aitta added in the Starport settings) ([AITTA_INSTALL_HELP]).

    AITTA=https://aitta.example util/serve_latest_release.sh someone/lamps 29500 ~/lamps-user

The key is ECDSA P-256 (Mbed TLS, in the tree); signing is deterministic
(RFC 6979), so a release packed twice is the same .sig. util/aitta_check.sh,
util/aitta_pin_check.sh, util/aitta_serve_check.sh and apps/aitta/check.sh are the checks.
