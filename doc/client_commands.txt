Client command sequence
=======================
The client can run a one-shot list of commands and then exit. Intended for
CI, visual checks of UI/rendering changes, and checking that an input action
actually registers.

Pass the sequence with -c. One command per line. When -c is given, the client
exits after the sequence finishes (exit status 1 if a command fails).

    $ bin/buildat -c $'delay 2000\nscreenshot /tmp/menu.png'
    $ bin/buildat -c @commands.txt
    $ bin/buildat -s localhost -c @commands.txt

-w WxH runs windowed at a fixed size without changing the size the client
remembers between runs. Use it for anything that compares images between runs.

-c ignores user/settings.json entirely and runs on the built-in defaults,
so a preference someone left at render_scale=0.5 can never change what a
screenshot looks like, and a run never writes the file. A -c run is also muted
unless -o says otherwise: nothing captures audio, and a driven run playing a
app's music through whoever's speakers is a small recurring annoyance with no
upside. -o still wins, which is how a preference itself gets tested:

    $ bin/buildat -s localhost -w 1600x900 -o render_scale=0.5 -c @check.txt

A -c run without -C keeps its cache in <cache>/scripted, apart from the
one a person's client uses: its log would push theirs out, and the pidfile
there names their local server ([SERVER_ADOPTED]).

@path reads the commands from a file. Empty lines and lines starting with # are
ignored.

-c - reads standard input instead, a line at a time, as it arrives. The client
keeps rendering and stays connected while there is nothing to read, and the run
ends at end of input or at a quit command. This is what to use when the next
command depends on what is on the screen: take a screenshot, look at it, then
send the next command. A line that does not parse is reported and skipped
rather than ending the run.

    $ mkfifo /tmp/cmd; sleep 900 > /tmp/cmd &
    $ bin/buildat -c - < /tmp/cmd &
    $ echo 'screenshot /tmp/now.png' > /tmp/cmd

The writer has to stay open -- the sleep above is what keeps it so -- because
closing the last writer of a fifo is end of input.

delay is wall-clock milliseconds of app time continuing to run. Use it for
what is a length of time itself -- a held key, a walk; startup, a screen,
the network and the meshes have wait_log, frames, sync and idle. Input is queued as
SDL events at the start of the frame (before Urho3D Input::Update). Screenshots
are taken after the current frame has been rendered (3D + UI), before buffer
swap.

The OS mouse is never captured or grabbed in -c mode, even if the app calls
SetMouseVisible(false). Use mouse_move for look (GetMouseMove); that is
relative and does not use a cursor position. mouse_pos is for a visible UI
cursor. look does the same pushing for you and waits for the camera to arrive,
which is what to use when the aim is what the shot is of rather than the
turning.

Real mouse and keyboard events are dropped for the duration of the sequence, so
neither the physical mouse nor typing aimed at another window can perturb a
run. Injected events still get through, as do escape and alt+tab.

The window is shown but never raised and never given input focus, so a
sequence can run beside whatever else is on the screen. Injected keys go
through Urho3D's Input path (GetKeyDown / GetKeyPress); Urho3D would drop them
while the window has no focus, so a running sequence forces its input focus
flag. Under Xvfb that is normally fine.

Commands
--------
delay <ms>
    Wait this many milliseconds before the next command. App keeps running.

A driven client is a window the desk did not ask for, and says so: its
WM_CLASS is "buildat-scripted" where a client somebody opened is
"buildat", its title is "Buildat Client (scripted)", and it maps
without raising and with _NET_WM_USER_TIME = 0, which a window manager
reads as do-not-activate. So a run does not take the focus of whatever
the desk is doing, and a window manager can put it somewhere else --
in icewm's winoptions:

    buildat-scripted.buildat-scripted.workspace: 3

SDL_VIDEO_X11_WMCLASS set by the caller is left alone.

wait_log <ms> <text>
    Hold the sequence until the client's own log has a line containing the
    text. Not seen in the time, the sequence fails and the client exits
    non-zero (read from standard input, a line says so and it goes on). A
    wait for a screen or a moment instead of a guessed delay:
    "wait_log 60000 the server put the player" and then "wait_log 60000
    scene, 0 undrawn within 2" is the world being playable (a substring:
    "0 undrawn" alone is also "110 undrawn"); "wait_log 90000 voxel
    types have their own textures" the same for the luanti_client extension.

    It waits for the *next* such line: what was logged before it started
    does not count, which is what makes "wait for it to happen again"
    work.

wait_log_any <ms> <text>
    The same, but the line counts wherever it appeared in this run. For
    something a program says once, and says while the sequence is still
    being read -- a launch UI that is slow to build says it is ready
    before the first command runs, and wait_log then sits out its whole
    timeout and every step after it runs that much late.

wait_log_absent <ms> <text>
    The time passes with no line containing the text since the command, or
    the sequence fails: a thing that must not happen.

frames <n>
    n frames rendered: the frame after an input has read it, a UI laid out
    and drawn after a click or a key. Where a delay of a second waited for
    a screen to redraw, frames 2 or 3 is the wait.

idle <ms>
    Until the client has nothing of its own still to do, or the sequence
    fails naming what was left. Looked at from the frame after the
    command (what the last command injected is read in that one) on:
    - the client's thread pool: meshes, collision shapes, the check of
      announced files, those a worker holds included (natively on worker
      threads, on the web the same tasks run a slice a frame on the
      page's thread); not the ray casts made again every frame;
    - the connection: files asked for and not in, announced files being
      checked, scripts held for them, packets read and not yet handled,
      one partly read;
    - fetches (buildat.http_get) not yet taken;
    - what client Lua registered with buildat.idle_source(name, fn):
      builtin/voxelworld's chunks to mesh (while the queue's front is in
      reach) and chunks held back for a remesh, builtin/luanti's textures
      to compose, extensions/luanti_client's objects to build.
    The client relights nothing (the server does) and has no tweens or
    background resource loads. What the server has yet to send is not the
    client's: a sync first, then idle, is "everything the server had for
    this is in and drawn".

        idle 100: not in 100 ms: pool tasks (meshes) 12, voxelworld
        chunks to mesh 40

sync <ms>
    A round trip through the server: a network:sync goes out, and the
    server answers it once every one of its modules has handled the client
    packets queued for it when the sync came (a module busy with a tick of
    its own is not waited for, unless a packet is queued behind it). The connection is ordered both ways,
    so on the answer what the client sent before it has been handled at
    the server, and what the server sent in answer has arrived and been
    handled here. A module's own later work (a thread of its own, a
    generator, an event it emits to another module) is not waited for. Fails with no server, or no answer in
    the time.

    util/web_drive.js has the three as steps (["frames", n], ["idle",
    ms], ["sync", ms]): a web page runs no command sequence.

expect_error <text>
    An error line containing the text is the drive's own doing, from this
    command on (each one: a provoked fault often logs its error twice).
    Otherwise **an error line in the client's log, or the connection to the
    server dropping, fails the sequence at once**, naming the line -- from
    the client's start until it shuts down, for a sequence read from a file.
    Lines at the head of the sequence are read before the client's first
    frame, so they can expect an error of its start.

screenshot <path>
    Write a PNG of the current framebuffer. Parent directories are created.
    Path may be relative to the working directory.

keydown <key>
keyup <key>
    Hold or release a key. Key names are SDL names: W, Space, Return, Escape,
    Left Shift, F1, Left, ... Aliases: enter, esc, shift, ctrl, alt.

keypress <key>
    Key down and up in the same frame. Use for taps (UI, GetKeyPress). Use
    keydown / delay / keyup to hold a key across frames (movement).

mouse_pos <x> <y>
    Set the client's mouse position to window pixel coordinates (backbuffer). For UI.

mouse_move <dx> <dy>
    Relative motion in pixels (GetMouseMove). Does not move the OS cursor.

    It goes straight into the frame's motion accumulator rather than onto
    the SDL queue, so the app reads exactly what was asked for; a pushed
    SDL_MOUSEMOTION could be flushed back out of the queue before Urho3D
    ever saw it, and something does that to the first one of a run. That
    one is still lost (2026-09-23): the delta reaches the accumulator and
    the app reads zero that frame, by a route that is neither
    SuppressNextMouseMove() nor ResetInputAccumulation(), both of which
    were instrumented and never fire for it.

    **So prefer `look` for aiming.** It pushes motion and measures what
    the camera did with it, over as many frames as that takes, which is
    immune to a lost push and does not need to know the app's
    sensitivity. `mouse_move` is the primitive under it, for an app whose
    camera `look` cannot read.

mouse_down <button>
mouse_up <button>
mouse_click <button>
    Buttons: left, middle, right (or 1, 2, 3). click is down+up same frame.

    A mouse_up waits for the frame that read its own down, so a hold is a
    hold of frames and not of milliseconds: on a client drawing a frame a
    second, a 1.4-second hold otherwise put its down and its up into one
    event poll and nothing polling the button ever saw it down. A held
    button the input dropped is pressed again, as a held key is.

click <type> "<label>" [x y]
    A left click (mouse_pos and mouse_click) at the centre of a UI element
    found by its type name (Button, LineEdit, CheckBox, Text, ...) and its
    label: a Text's or a LineEdit's own text, otherwise its first child
    Text's. The label is exact, or a prefix with a trailing *; it cannot
    hold a ". The element is effectively visible, and the element under its
    centre is it or a child of it, so nothing (a dialog, a dropdown's list)
    is over it. Of several, the one nearest x y, in mouse_pos pixels.
    None fails the sequence, and the error lists every element of the type
    with its rectangle and why it was left (another label, hidden, covered
    by what). For the checks that clicked at fixed pixels and missed
    silently when a row moved; move one to it when it is next touched.

        click Button "Accept" 283 154
        click Button "No invites*"

mouse_wheel <delta>
    Wheel ticks. Positive is away from the user.

tap <x> <y>
    A finger down and up at x, y (TouchBegin and TouchEnd in one frame):
    the touch controls with BUILDAT_TOUCH=1, natively.

finger_down <id> <x> <y>
finger_move <id> <x> <y>
finger_up <id>
    One finger of up to nine (id 1-9), each a step: a drag is a down, moves
    with delays between them, and an up; two fingers down and moved make a
    pinch or a two-finger scroll. finger_up lifts it where it last was.

    BUILDAT_TOUCH=1 natively is a touch mode: the touch controls, and the
    UI scaled as on a phone (one UI pixel to a CSS pixel at least, half
    again for a finger, 400 UI pixels across the short side at most). Run
    by hand (no -c), the mouse is a finger.

look <yaw> <pitch>
look_dir <x> <y> <z>
    Aim the camera and wait until it is aimed. Degrees: yaw from +Z towards
    +X, pitch positive upwards; look_dir takes a direction and works out the
    same two angles.

    Nothing here knows what app is running. The camera is turned by injecting
    mouse movement and watching what the camera of viewport 0 does about it:
    how far a pixel turns it, and which way round, is measured from what the
    last frame's push actually did, so an app with its own sensitivity or its
    mouse look inverted is aimed as well as any other. A push that changes
    nothing is tried the other way before it is believed.

    The command ends when the camera is there, which is usually three or four
    frames. An axis that has moved and then stops answering in both directions
    is against a limit the app keeps -- a pitch clamp, most of the time -- and
    the command ends with a warning naming where it stopped. A camera that
    never moves at all, or a viewport with no camera on it, is not an app this
    can aim: the sequence fails and the client exits non-zero.

text <string>
    SDL text input (UI text fields). Rest of the line is the string.

event <name> [param]
    Send the Urho3D event command_seq:<name> on the client, with the rest of
    the line as its string field Param, at this point in the sequence. Any
    client Lua may subscribe to it (the command_seq: prefix is on the
    sandbox's safe list); the runner knows nothing of the names. The reply,
    if any, is a line in the log, which is what a test reads.

    The receivers in apps/vanilla's client (builtin/luanti):

    event scan <resolution> <label>
        Logs, under `scan <label>:` lines and ending in `scan <label>: end`,
        what the client sees: a `self` line (position, yaw, pitch, hp, the
        wielded item, the hotbar), the eye voxel's `light sky`/`lamp`, one
        `hud` line per HUD element with its rectangle, the crosshair's hit,
        a <resolution>x<resolution> grid of bins with the voxel each bin's
        ray hits within ten voxels (and what it passed through), one
        `object` line per object on the screen with its screen position,
        and every element of an open form with its text, image and
        rectangle. All rectangles are in window pixels, the coordinates
        mouse_pos takes. A screenshot in the same sequence line pairs with
        it; drive.py reads the block after every turn.

    event scan_volume <radius> <label> [light]
        Logs the voxels in a cube of that radius around the player, one
        row per column, as names -- or the light nibbles with `light` --
        which drive.py keeps as its map.

    event look_body
        Turns the view to the nearest fallen body's centre and logs
        `look_body: at x, y, z` or `look_body: no body`.

    event status_text <text>
        Shows the text at the top right of the screen in the harness's
        pale yellow, replacing the previous one; an empty text clears it.
        drive.py writes the rule it is about to act on, so a person
        watching the run sees what it is attempting.

    The receivers in extensions/launch_world (the launcher room):

    event room probe|ornament|still|attract|dissolve [bay]
    event room preset <n>
    event room station wall|floor|terminal
        The room's switches for a scripted run, in place of keys:
        extensions/launch_world/README.txt. The same switches at boot,
        and the room's other knobs (the options rounds ARCH, LIGHT,
        SOUND, PRESET; PITCH, the probe, the tonemap, ...), are
        BUILDAT_LAUNCH_* environment variables, listed there under
        "Environment".

    event mode menu
        Closes whatever is over the room and goes to the standing place,
        so a sequence does not have to know which mode it left the room
        in.

quit
    Stop the sequence early. The client always exits at the end of -c anyway.

Example
-------
Wait for the launcher room, screenshot it, click a point, screenshot the
screen it drew:

    wait_log_any 60000 the room hums
    screenshot /tmp/buildat_menu.png
    mouse_pos 400 300
    mouse_click left
    frames 3
    screenshot /tmp/buildat_after_click.png

Take the same shot every run, whatever the camera was left pointing at,
of the world drawn:

    wait_log 60000 the server put the player at
    look 275 -15
    idle 30000
    screenshot /tmp/buildat_view.png

Hold W for half a second while connected to a local server, and shoot
once the server has had the walk and the client the answer:

    wait_log 60000 the server put the player at
    keydown W
    delay 500
    keyup W
    sync 5000
    idle 10000
    screenshot /tmp/buildat_moved.png
