Developer notes
===============
Small things worth knowing when working on the engine itself. Conventions
are in conventions.txt; Magic's changes to Urho3D in magic.txt.

Magic: scene replication
------------------------
Always pass LOCAL or REPLICATED as the CreateMode to Node::CreateChild() and
Node::CreateComponent(). Leaving it to the default causes wrong replication
at a point far from the call.

Magic and Urho3D
----------------
Magic is the fork's name (magic.txt); inside it the namespace is still
Urho3D's, so magic.X in Lua and magic::X in C++ is Urho3D::X.

Profiling the client under callgrind
------------------------------------
The client's stack is deep with Lua bindings, and callgrind folds it into
one <Cycle N> unless told to separate:

  valgrind --tool=callgrind --separate-threads=yes --separate-recs=10 \
      --separate-callers=5 bin/buildat -s localhost

Profiling a Luanti game's Lua
-----------------------------
See "Finding out what is slow" in luanti_module.txt: BUILDAT_LUANTI_LUAPROF,
the per-mod load times, and util/bench_worldgen.sh.

Backtraces
----------
A crash prints a symbolised backtrace on Linux (src/impl/linux/debug.cpp). Under a
scripted run the client's log carries it; fuzz.sh and drive.sh read
"Crash:" as a failure.

Simulated time
--------------
`buildat_server --sim-clock` runs the calendar ahead of the real clock by
the seconds in <user_path>/sim_clock, read every tick; a check writes the
file in place (`echo N > sim_clock`) and waits for the log's "sim clock:
Ns ahead". Dates, expiries and the limits per hour or day read
interface::os::wall_us(); timeouts, budgets and TOTP stay on
interface::os::time_us(). A jump is one tick: what runs on the calendar
compares against it. A server's Starport announcer announces at once after
a jump. The option is only on the command line. util/sim_clock_check.sh
runs a Starport, a Hearth and an Aitta through 183 days and 5 years.

`buildat_server --sim-rate N` ([CHECK_TIME_SCALE]) runs the game faster:
each tick is still 1/30 s of game time, N times as often (0: as fast as
the modules take them), and a late tick runs late rather than being
dropped, so the game is the same on a slower machine, only slower. The
rate is a ceiling. It implies --sim-clock: a second number in sim_clock
is the rate from then on (`echo "0 1" > sim_clock`). What the game does
over time reads interface::os::game_us(), the ticks' clock under the
option and time_us() without it; the game's seconds go to
<user_path>/game_clock. A check waits on them: check_lib's
wait_for_log with the user path as a fourth argument, and a drive's
game_clock and game_rate commands (doc/client_commands.txt). A client
whose prediction runs on the wall clock is told the rate
(os::game_rate(); hillclimb's "hillclimb:rate"). util/sim_rate_check.sh
checks it.

Sanitizers and fuzzing
----------------------
cmake -DSANITIZE=address in a build directory of its own (Build/asan)
builds with ASan; the server then compiles its runtime-compiled modules
with the same -fsanitize (BUILDAT_SANITIZE in src/server/rccpp.cpp), and
the module cache keeps the two builds apart. Run it with
ASAN_OPTIONS=detect_leaks=0:abort_on_error=1.

util/fuzz/ ([SECURITY_RUN_1]), its corpora and crashes kept under
local/security/fuzz/:
- fuzz.sh [seconds] [target ...]: libFuzzer harnesses (clang, ASan and
  UBSan) for compress, packet_stream, voxel_volume, json, zip, image,
  markup (with an oracle for tags, attributes and link schemes), font
  and wasm (a module's .wasm through the client's checks and meter,
  WABT's writers and WAMR's interpreter; seeded with the .wasm the
  checks' servers built, so run apps/sample_wasm/check.sh first)
- proto_fuzz.sh: a server fuzzed by a peer (PUBLIC=1, APP=floorplanner,
  GAME=, BUILD=asan; CORPUS= mutates a session record_proxy.py recorded)
- client_fuzz.sh: a client fuzzed by a hostile server; SANDBOX=1 sends
  sandbox_fuzz.lua, which calls the sandbox's API with values at the edges
- game_fuzz.sh: sandbox_fuzz.lua from inside a loaded vanilla game
