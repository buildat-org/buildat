Buildat conventions
===================
Coding style, naming, exceptions, threads, the directory layout, commit
messages and the coordinate convention. Read before the first commit.

C++ Coding style
----------------
Using the correct coding style is important. If you are asked to fix your style
to follow the one defined here in every detail, do it carefully.

If something is found to be missing from this document, such additions shall be
made.

Identifiers:
- Class and struct names are CamelCase,
- All function names are lowercase_with_underscores,
- All variable names are lowercase_with_underscores,
- All member variables start with m_. If the struct in question is a stupid data
  container, this does not need to be followed.

Never use "class", always use "struct".

Prefer lightweight interfaces with a creation function for the default
implementation, like "struct State" and "State* createState()". The default
implementation can be called "CState" in this case, if an obviously better name
does not exist.

Use std::unique_ptr and std::shared_ptr. (core/types.h: up_<> and sp_<>)

Header files must have zero preprocessor conditionals, with the exception of
headers in src/ports/.

Function naming:
- Suffix _u: Unsafe, not included in public interface

Naming:
- "type": Numeric id representing a type
- "name": A string; generally works as an identifier but not necessarily
- "id":   Numeric id of an instance of something that is not a type
- "sub":  Subscription; a means to trigger something based on something else
          happening; data goes from the emitter to the subscriber
- "hook": A callback that can modify some of the source's data or behavior
          before the source goes on with it

Logging:
- Use core/log.h. Only use stdout directly in case of an interactive command
  line interface (like printing errors for command line arguments).
  The logger writes a control byte other than a tab or a line break as
  \xNN, so a peer's bytes in a line cannot move the terminal.

Ordering of #include directives:
1) The interface that the current file implements, ""
2) Internal interfaces, from core-ish to utility-ish, ""
3) Bundled libraries, <>
4) Installed libraries, <>
5) STL headers, <>
6) System headers, <>

Exceptions
----------
Do not use assert(); throw anonymous exceptions instead:
- if(fail) throw Exception("Thing failed");

In normal operation, zero exceptions should be thrown. Unless any potential bugs
are occurring, you should be able to play the game fine if you set a breakpoint
on a GCC Linux build to __cxa_throw, which will stop the program immediately
when an exception occurs.

Exceptions are allowed to occur when a resource has expired that the caller had
to expect to still be valid in order to avoid some kind of ridiculous code
structure.

Non-exception throwing and exception-throwing methods
-----------------------------------------------------
- get_x: Returns nullptr or equivalent if not found
- find_x: Returns nullptr or equivalent if not found
- check_x: Throws NullptrCatch if not found

To check for nullptr returned by get_x() or find_x(), use the check() function
in core/types.h.

Threads
-------
The program should always be debuggable with Helgrind and DRD, without false
positives.

Only use synchronization primitives that wrap pthreads, because that is what
Helgrind and DRD support.

If an object owns a thread, the thread should not be stopped in the object's
destructor. Instead the object should have thread_request_stop() and
thread_join() methods which should always be called before the object is
destructed. This allows fast parallel shutdown and better control over
destruction. You can skip this if you somehow can do it without Hellgrind and
DRD bitching at you though.

Directory structure
-------------------
├── 3rdparty    << Bundled 3rd-party libraries
├── Build       << Build files; "mkdir Build; cmake ..; make"
├── cache       << Runtime directory used by Buildat; a sandboxed server's
│                  is cache/apps/<app>, and cache/rccpp_build only the
│                  unsandboxed build's, read by the sandboxes; the client keeps
│                  a server's files in cache/remote/server_<address>
│                  (this machine's servers share cache/remote/local),
│                  and a client run with -c and no -C uses cache/scripted
├── builtin     << Built-in modules
├── client      << Built-in client files
│   └── extensions << The client's own extensions, trusted: the sandbox
│                  itself (urho3d, magic_sandbox, uistack, replicate),
│                  network, starport, sandbox_scan
├── extensions  << Client extensions, run in the Lua sandbox
├── src
│   ├── client  << Client-specific code
│   ├── core    << Core code (must be kept minimal but sufficient)
│   ├── impl    << Interface implementations
│   ├── interface << Interface available to modules
│   └── server  << Server-specific code
├── apps       << Apps that can be run using buildat_server -m <path>
├── doc         << This documentation
├── user        << The user's data -- never in git: apps/<app> an app's own
│                  (its saves, vanilla's imported worlds), shared/<app>
│                  what it shares read-only with the others (vanilla's
│                  Luanti games and settings), installed/<author>/<name>/
│                  <version> the Aitta apps (aitta.txt), and the engine
│                  settings
├── local       << Runs' outputs: fuzz and driven runs, reference shots,
│                  options filed for the user -- never in git
└── util        << Development utilities: packaging, the release, benches,
                   the fuzzers (util/fuzz/fuzz.sh: libFuzzer targets;
                   proto_fuzz, client_fuzz, game_fuzz: whole programs)

Checks
------
A check is one shell script that runs the thing and decides for itself.
util/check_lib.sh is the checks' kit and carries the contract ([CHECK_KIT]):
exit 0 passed, 1 failed, 77 could not run, and the last line is "PASS: ",
"FAIL: " or "SKIP: " with what was actually measured in it. A check that
prints a failure and exits 0 is the fault this contract exists for. The
kit besides: fail and skip, check_tmp (a temp directory removed at exit
with its pids stopped; KEEP_TMP keeps it), wait_for_log, start_server
<log> <ready-regex> <timeout_s> <port|auto> <command...> (a port already
taken fails at once, naming its owner; auto picks one in 29700-29999),
and check_pgrep / check_pkill, which match only processes run with the
checks' user path, so a check never touches a playtest's. util/uidrive.py
is the scan parser and a fifo-driven client for a UI drive.

Five header lines say the rest, and only the first is required:

  # tier: quick        quick (no downloaded game, what a push runs), full
                       (wants the game media), long (fuzz, drives, shots),
                       broken (fails for a reason of its own, not the
                       code's: run alone or with run_all.sh broken while
                       it is fixed, and in no other tier; --changed picks
                       from a tier, so it is left out there too)
  # broken: <why>      with tier broken: the tier it goes back to and its
                       recorded failure, in a few words
  # cost: 24s          a seed; local/run_all/costs is measured per machine
  # covers: <paths>    what it proves OUTSIDE its own tree; where it lives
                       is covered already -- extensions/<x>/check.sh, and a
                       core.sh beside it, cover extensions/<x>/**
  # flaky: <why>       run and reported, but it does not decide the status
  # always: yes        appended to every --changed pick instead of competing
                       to be the cheapest runner for a file; for a check so
                       cheap it may as well run (lua_syntax.sh, under a
                       second), which would otherwise push the deep runners
                       out of the pick by costing less than all of them

util/run_all.sh <tier> runs a tier, every script git knows with a
"# tier:" line (a runner under apps/<a>/ covers apps/<a>/**); --changed
[range] runs the cheapest runners that cover what git says changed, which
is the regular check. util/check_contract.sh reads every runner for the
contract and names the ones whose exit status cannot say FAIL.
A runner is never retried: a check run three times and taken at its best is
how a real fault becomes a known flake.

A check is run to learn something, not to perform diligence: a change already
verified directly -- a probe that drove it, a screenshot of the thing itself,
a number read out of the log -- does not then run the suite that covers
neighbouring behaviour. Run the runner for what the change might have broken
that you did not look at. Watching a twenty-minute suite re-prove what a
screenshot already showed is the cost the tier exists to avoid (user,
2026-09-25).

A change runs the runner that covers it, and the tier is what a push runs.
Twenty minutes is never the right answer to a one-word change. Where the full
runner is dear, the tree carries a core one beside it -- one client and well
under a minute, the paths an edit breaks (extensions/launch_world/core.sh
against check.sh) -- and that is what an edit runs.

An app's look is checked by a runner and not by memory: a change under
builtin/voxel_shading, the mesher or voxelworld picks
apps/sample_lighting_scene/check.sh through its "covers" line. That one compares the
fourteen framings against the reference run kept in local/sample_lighting_scene/ref/
-- taken with --accept on a tree whose look somebody has confirmed -- and says
which view moved and by how much. With no reference on the machine it skips
and says so; a committed baseline is [CHECK_BASELINE]'s and wants a commit
hash the user has picked.

A drive progresses on events, not on time (the user, 2026-10-13): wait_log
and wait_log_any are what move a sequence on. delay is for two things only:
- what needs a length of time itself -- walking the player for a while, a
  double click, a timeout doing what it is for;
- a settle of at most 2 s after a wait, where a more targeted log line would
  be awkward or spammy, or where the thing checked happens a few ticks after
  the line.
A delay that is neither gets a log line to wait for: one line where the thing
happens, not a stream. A delay that stays says which kind it is in a comment
where that is not obvious.

A drive fails fast. A wait that times out fails the sequence and the client
exits non-zero at once; a thing that must not happen is wait_log_absent. An
error line in the client's log, or the connection dropping, fails it then and
names the line; an error a drive provokes on purpose is declared first with
expect_error. A timeout is a small multiple of what the event takes on the
slowest machine the runner runs on, not a round minute. The shell side the
same: a runner stops at its first failed step and kills what it started, and
a runner waiting for a server, a file or a port polls that thing
(wait_for_log in util/check_lib.sh) rather than sleeping.

A drive's waits say what they are waiting for, and the line they print is in
the log the verdict greps: a grep whose pattern the drive also carries counts
the wait's own line and passes by itself. Filter wait_log out, or grep for the
line's own source (launch_w:, not the text alone).

Under BUILDAT_CI=1 a timing is a row and never a verdict -- what CI asserts is
behaviour, since a threshold argued against a desk's GPU fails every run under
llvmpipe and teaches everyone to ignore the result.

Commit messages
---------------
Present tense, describing what the commit leaves in the tree rather than the
work it took. Where it fits, start with the place (a module, a script, a
directory). When the change belongs to something tracked, end with its
reference in brackets -- a ticket's number or a plan codename -- so the
history and what it answers lead to each other:

- voxelworld: a dug blocker starts dark and the flood fills it from around it [DIG_LIGHT]
- launch_menu: the local app list pages at fifteen [#42]
- drive: a run has a goal rung and ends when it is met [DRIVE_GOAL]
- 3rdparty/Urho3D: a virtual mouse position for the scripted client [SEQ_MOUSE_FREE]

A change that answers nothing tracked needs no reference.

No marketing. A message describes the final diff: a fix that was made and
undone before the commit is not in it.

Coordinates
-----------
Urho3D's convention, unchanged: left-handed, Y up, +X right, +Z forward. It is
the Direct3D convention, and the one Unity uses.

Rotations are in degrees. Yaw turns around Y and grows turning right, so yaw 0
looks towards +Z and yaw 90 towards +X. Pitch turns around X and grows looking
down. This is the order Quaternion(pitch, yaw, roll) takes them in.

Voxel coordinates are the same axes, and a voxel is centred on its integer
coordinate: it spans from -0.5 to +0.5 around it (impl/mesh.cpp shifts the
PolyVox vertices by that half unit).

Content authored elsewhere generally is not in this convention. glTF is
right-handed, and Blender is right-handed and Z up. The glTF loader converts
(3rdparty/Urho3D/Source/Urho3D/Graphics/GLTFLoader.cpp); anything else that
imports geometry has to.

Client-side Lua
---------------
Everything the client runs (client/, extensions/, every client_lua/) parses
as Lua 5.1, the web client's PUC Lua: no goto, and no LuaJIT-only string
escapes ("\u{...}", "\x41", "\z"; write the UTF-8 character or a decimal
byte escape). A native build checks both (luac51 -p and
util/lua51_escapes.cmake) and fails at the file and line.

Magic
-----
The engine is Magic, Buildat's fork of Urho3D 1.7.1 (magic.txt); code names
it `magic`, not Urho3D. See magic.txt before patching it.


Menu screens
------------

Escape is Back, on every screen the launcher and the apps draw: what the
screen's "< back", "Back", "Cancel" or "Ok" button does, Escape does,
whether or not a text field has the focus. The one place it is is
ui_utils.bind_button_menu (extensions/ui_utils), which every vertical_menu
and grid goes through: it presses the item labelled as the way back. A
screen with a capture of its own (the key editor listening for a key)
takes Escape first by returning true from its on_key handler, and Escape
is then that capture's cancel. A screen never adds a second Escape handler
that pops itself -- with the menu's own, that was the pop twice.

A click or tap on nothing is Escape, and so is the browser's Back
([TAP_BACK], client/core/uistack): a touchscreen has no Escape key.
Not on the first screen on the stack, where Escape would be Quit; there
the browser's Back leaves the page. A layer over a world, where a click on
nothing is the game's, is pushed with {tap_outside = false}.
A screen also has a "×" at its top right (ui_utils.close_glyph,
[CLOSE_GLYPH]), for a screen that fills a phone's: it does the same Escape.
Such a screen has no Back or Close that only closes it; a vertical menu of
buttons keeps its "< back" and has no ×.

Every menu is by the keyboard without a line of its own ([MENU_KEYS]): a
page made with ui_utils.keyboard_page (every Accounts page through its
page_window, floorplanner's pages) or a menu through bind_button_menu /
vertical_menu gets the arrows, Tab and Enter. No letter shortcuts
([NO_LETTER_KEYS], user 2026-10-07): a label is what it says.
