Buildat Client API
==================
The Lua API an app's client_lua and an extension see: buildat.*, the
sandboxed magic (Magic, Buildat's fork of Urho3D), the built-in extensions' safe interfaces, and
the voxel data model as Lua reads it. Rewritten against the code
2026-09-21 ([CLIENT_API_DOC]); util/api_names.py --check says whether it
still matches, and its last section is generated by that script.

Lua code is run in two subtly different environments: the extension
environment (the client's own code, client/ and client/core/, plain
Lua, no rules) and the sandbox (everything a server sends, a launcher
file's tiles, and every extension under extensions/). What a name is in
each is said with the name.

Terminology: a *voxel* is one cell of a voxel volume, and a *node* is a scene
node -- what a Scene holds and a component hangs off. Apps that come from
elsewhere may call a voxel a node (Luanti does); in buildat it is a voxel.

=====================================

buildat.open_import_folder() -> ok, err
- Opens <user>/shared/<the local server's app>/import in the desk's file

buildat.get_sound() -> mute, db; buildat.set_sound(mute, db) -> ok, err
- The one preference an app may write: the player's ear, from a pause menu.
  Through the preferences' own parser and file, so the launcher's page and
  the app's row agree.
- The volume is decibels below full ([VOLUME_LAW]): 0 is full, the settings
  step 3 dB down to -30, and -33 or less is off. The gain is made from it in
  the client, in the one place it is applied.

buildat.get_render_scale() -> share, automatic
buildat.set_render_scale(share or "auto") -> ok, err
- A second preference an app may write: render_scale (see "Engine
  settings"), from an app's own settings, since the web client has no
  launcher to reach Engine settings through. The frame's cost, not its look.
- "auto", the default, is the client's choice, made again at each start and
  resize: natively 1; on the web about 2.1 M pixels (1080p's) of the page's
  canvas for the 3D, at most 0.5 on a screen over 3000 device pixels on a
  side or on a software renderer, rounded down to 1, 0.75, 0.67, 0.5, 0.33
  or 0.25.

buildat.get_ui_size() -> the UI scale now, automatic
buildat.set_ui_size(scale or "auto") -> ok, err
- A third preference an app may write: ui_size (see "Engine settings"), for
  the same reason as render_scale. "auto", the default, follows the window
  (the short side over 1080); a scale is 0.5 to 3. It takes at once, and a
  set_ui_scale() of the app's own wins over it.

buildat.take_screenshot() -> file name, or nil and why not

- Puts a directory on Urho3D's resource search path, so files written there can

buildat.compose_image(args) -> width, height
buildat.set_web_fullscreen(bool)
- On the web client on a touchscreen: whether the page goes fullscreen, which
  is the only way to put a phone browser's address bar away on a page that
  does not scroll. Entering waits for the user's next tap (a browser only
  allows it from one); leaving is at once. Off by default; nothing natively.

buildat.get_cache_path() -> string (sandbox only, see below)
buildat.create_directories(path) -> bool (unsafe Lua only)
- The directory and its parents, for trusted Lua keeping a file of its own
  under the user path; a path is not a thing an app gets to name
buildat.set_watchdog_seconds(n) (unsafe Lua only)
- How long without a frame before the watchdog logs this thread's stack;
  0 puts the default (10) back. A screen that waits lowers it. Apart from
  that, on Linux 30 s without a frame errors the running script out to its

  60 s (exit 3).
- In the sandbox as they are (decided 2026-09-13): what they give sandboxed
  code is "write files under the cache and make them loadable", which a server
  can already do through client_file. The cache-path check in each is
  load-bearing: anything added beside them writes under the cache or it does
  not go in the sandbox.

buildat.write_floats(vector_buffer, values)
- The values into the buffer as floats, replacing what was in it
buildat.write_shorts(vector_buffer, values)
- The same as 16-bit samples, each floored and clamped to -32768..32767

A sound made of samples is played two ways. A magic.BufferedSoundStream
is topped up ahead of its playhead (launch_world's synth). A magic.Sound
made from samples ([SOUND_FROM_SAMPLES], buildat.has("sound_from_samples"))
is made once and played by any number of SoundSources, as a loaded one:
  local sound = magic.Sound:new()
  sound:SetFormat(rate, sixteen_bit, stereo)  -- rate 1000..96000 Hz
  sound:SetData(vector_buffer)                -- once; little-endian
  sound.looped = true                         -- if wanted
The format goes first and the data once: a Sound's samples are not
replaced under a source playing them. A Sound holds at most 8 MiB, and
the Sounds made from samples and alive at most 64 MiB together; over
either SetData raises with the reason.

buildat.synth.buffer(n) -> a buffer of n samples ([SYNTH_BLOCKS],
  buildat.has("synth_blocks"))
- Samples held in C++, floats, -1..1 for full scale, and the blocks that
  write them: Lua builds a chain and C++ runs it, so a sound is a few calls
  and not one a sample (the web's Lua is interpreted). A buffer holds at
  most 2^21 samples (47 s at 44100 Hz), the buffers alive 2^24 together.
  Indices and spans are in samples from 0: `from` defaults to 0 and `n`
  to the rest.
- **The same samples everywhere**: a block's output for given inputs is
  the same natively and on the web, and in every release
  (doc/compatibility.txt). A block that changes is a new block.
buf:len(), buf:get(i), buf:set(i, v), buf:clear([from, n])
buf:gain(g[, g_to, from, n])
- Multiplied by g, ramped to g_to over the span.
buf:mix(src, src_from, dst_from, n, gain[, gain_to])
- src's samples summed in, the gain ramped so that a cut does not click.
buf:to_shorts(vector_buffer[, from, n]) / buf:from_shorts(vector_buffer
  [, dst_from]) -> n
- To and from 16-bit samples in a VectorBuffer: what a
  BufferedSoundStream's AddData and a Sound's SetData take.
buf:hash() -> 16 hex digits, the samples' FNV-1a
The blocks write over a span and take a table; each has rate (Hz,
1000..192000, 44100 by default), from and n. A curve is a number or a
table, its rates per second, evaluated per sample from the span's start:
  {start, slide (added a second), mul (multiplied in a second, > 0),
   accel (mul's own multiplier a second), wobble and wobble_speed
   (times 1 + wobble sin(2 pi wobble_speed t)), jumps = {{t, factor},
   ...}, restart (seconds: back to the start, jumps too), min, max}
buf:osc{wave, freq, duty, phase, oversample}
- wave "square" (duty 0..1, a curve), "saw", "triangle" or "sine"; freq a
  curve in Hz; oversample 1..16 subsamples averaged, so a square high up
  does not alias. Written over the span.
buf:noise{kind, seed, freq, oversample}
- "white", a new value a sample, or "held" (sfxr's): 32 values a period
  of freq, each held. seed 0..2^32-1. Written over the span.
buf:filter{type, cutoff, resonance}
- In place: "low", "high" or "band"; cutoff a curve in Hz, up to a fifth
  of the rate; resonance a curve 0..0.99.
buf:delay{delay, max_delay, feedback, mix}
- In place: delay a curve in seconds, up to max_delay (at most 2);
  feedback -0.99..0.99; mix 0..1, the delayed part. A phaser, a flanger
  or an echo. The line starts empty each call.
buf:envelope{points = {{t, v}, ...}}
- Multiplied in: linear between the points (t in seconds, ascending).


The extension environment
=========================

The client core (client/core/: aitta, magic_sandbox, network,
replicate, sandbox_scan, starport, uistack, urho3d) and the boot-up code
run in the extension environment: a raw Lua environment with no sandboxing or
other rules. An extension under extensions/ runs in the sandbox
([EXTENSIONS_SANDBOXED]): its init.lua is run as a server's script is, its
other files through buildat.run_extension_file(), and it keeps files with
storage_read/storage_write and cache_read/cache_write.

Extensions use the new Lua 5.1/5.2 module interface. An extension that wants
to give sandboxed code an interface returns a table with a "safe" field
holding it; sandboxed code that requires the extension gets a read-only view
of the safe table and nothing else ([SAFE_TABLE_PATCH]: reads go through,
an assignment raises). Sandboxed code uses
  <name> = require("buildat/extension/<name>")
  <name> = require("buildat/core/<name>")  -- a part of the client core
and the client core adds .safe for another's safe interface.

An extension with no safe table cannot be required from the sandbox at all
(the require raises), but it is loaded first, so its top level runs: an
extension's load must be inert until something calls through its safe table
([UI_UAF]).

API specific to the extension environment:

buildat.connect_server(address)
- Address may include port in format "host:port" or "[host]:port"

buildat.list_apps() -> {{name, size, kind}, ...}, the apps under apps/

buildat.list_launchers() -> {{kind, name, path, launcher = bool}, ...}

- Starts buildat_server as a child on a free port with -m apps/<app>, and

buildat.local_server_running() -> bool

buildat.random_bytes(n) -> n bytes
- From the platform's cryptographic random source; 1...1024 bytes

buildat.bignum
- Arbitrary-precision unsigned integers, for what is too slow or too fiddly to
  do in Lua. Numbers are big-endian byte strings and come back with no leading
  zero bytes ("" is zero).
- add(a, b), mul(a, b), mod(a, m), sub_mod(a, b, m), mul_mod(a, b, m),
  mod_exp(base, exponent, m)
- What is built on these belongs in Lua; extensions/luanti_client/srp.lua is an
  SRP-6a login written that way.

buildat.list_preferences() -> {name, ...}
buildat.get_preference(name) -> number, boolean or string, nil for an unknown
  name
buildat.set_preference(name, value) -> true, or false and why
- The settings under "Engine settings" below. The C++ side is the
  authority: set_preference() parses and range checks a value through the same
  code -o goes through, applies what takes effect now -- the sound gain, the
  frame limiter, vsync and MSAA, the render scale -- and persists the rest.
- A preference is the user's: app code a server sent can read one --
  default_username is the name an app offers when it asks for one -- and
  set_preference refuses it. A launch extension, which is the user's, can set
  them.
- extensions/launch_menu/preferences.lua is the screen over these.

buildat.read_image(resource_name) -> width, height, rgba
- The pixels of an image, as one string of four bytes per pixel, row by row.
  For whoever has to look at them rather than draw them: a colour palette.

buildat.extension_path(name) -> the extension's directory

buildat.connect_server_start(address), buildat.connect_server_poll() -> state
- The connect off the frame: start it, then poll from an Update handler until
  it answers. The blocking connect_server() freezes the frame for as long as

The sandbox environment
=======================

All code sent by the server to the client runs in the sandbox environment,
and so does a launcher file's tile list.

Extensions are accessed with require("buildat/extension/<name>") and the
client core's parts with require("buildat/core/<name>"); each is the
equivalent of the same require's .safe in the extension environment.
buildat/extension/<core part> is the name before 0.7.10 ([CLIENT_CORE]),
kept as an alias of buildat/core/<core part> until the next break: the
same table. Served client Lua that is to run on a client before 0.7.10
uses the old name. require("buildat/module/<name>") gives a module's
client half.
Nothing else can be required: not the standard libraries, not a path.

API specific to the sandbox environment:

buildat.is_in_sandbox -> true

- Copies the table's contents into the current global sandbox environment. It
  will still not leak into the scope of other files running in the sandbox.
  Useful for dropping the "namespace table" of an extension.

  restarting it); if connected from the command line, close the client

The launch UI's own verbs
-------------------------

A launch extension is a slot anybody can fill, so it has to run in the sandbox
every app runs in ([LAUNCH_SANDBOX]). The rule that keeps this list short is
that the trusted side owns the verbs and the sandbox owns the drawing: each of
these does one nameable thing, and none is a general capability, because every
addition here is attack surface for every app too.

  is what the sandboxed launcher files built ([LAUNCH_GRID]).

  names a launch UI shows and filters by, and either may be absent.
- last_launched is unix seconds, and absent for a key that never was, so a
  launch UI can sort by recency without keeping a list of its own

Safe interfaces of built-in extensions
======================================

Use extensions in this way:
  cereal = require("buildat/extension/cereal")
  cereal.binary_output(...)

You can use sandbox.make_global like this:
  sandbox.make_global(require("buildat/core/urho3d"))
  local scene = Scene()

The members of each safe table are listed by name in the generated section
at the end of this file; what follows is what they are for.

cereal
------
cereal.binary_input(data: string, type: object) -> value: <any>
cereal.binary_output(value: <any>, type: object) -> data: string

Example usage (by using an object as the base structure for value):
	type = {"object",
		{"a", "byte"},
		{"b", "int32_t"},
		{"c", "double"},
		{"d", "string"},
		{"e", {"array", "string"}},
		{"f", {"object", {"x", "int32_t"}, {"y", "int32_t"}}}
	}
	input_value = {
		a = 128,
		b = 1000,
		c = 3.14,
		d = "Foo",
		e = {"Bar1", "Bar2"},
		f = {x=1, y=2},
	}
	data = cereal.binary_output(input_value, type)

	-- Data can be now sent over network or be saved on disk

	output_values = cereal.binary_input(data, type)

A record, as a C++ interface::Record writes it (doc/architecture.txt):
	{"record", major, minor, type}
read, another major is an error and the fields a newer minor added at the
end are skipped. An older minor's record, its type an object, reads with
the fields it lacks at its end at their type's zero value: 0, "", {} for
an array or a map, and an object's (or a record's) fields each the same.

urho3d (magic)
--------------
Whitelist-based wrapper for Magic's Lua API; the sandbox sees it as the
global "magic" and, through sandbox.make_global, as Magic's globals
themselves. The whitelist is in client/core/urho3d/safe_classes.lua (the
classes, their methods and properties), safe_globals.lua (the constants and
the global functions) and safe_events.lua (which events reach the sandbox,
and which fields of each). The classes and every member of each are in the
generated section at the end; a class or a member not there does not exist
in the sandbox -- a property missing from the whitelist makes a feature
silently do nothing, which is why util/whitelist_sweep.py exists.

What is refused, and why:
- Audio:SetMasterGain("Master") -- the user's volume, see "Engine settings"
- Renderer:SetViewport() and its siblings -- magic.set_preferred_viewports()
  is the way, so the user's render scale applies
- Anything that reaches a file path, the environment or another process. A
  resource name the cache is asked for is relative, with no ".." and no ":"
  (safe_classes.lua's resource_name_ok): Urho3D's ResourceCache falls back
  to an absolute path outside every resource dir.
- UI:SetClipboardText() except within a second of the user's own key or
  click ([SECURITY_RUN_1]), as a browser asks.
- A UIElement's priority above 999: the client's own dialogs are drawn over
  every script's element. RemoveAllChildren() leaves the client's own
  elements (named "__trusted..."), their color reads as white, and a
  client's secret field reads "" and keeps its name ([TRUST_COLOR]).
- A property whose Urho3D type is a const reference has no setter (see the
  replicate section below); where it matters the class's own setter function
  is exposed instead

A removed UIElement is dead to the sandbox ([UI_UAF]): a wrapper held past
its element's removal raises on any access instead of reading freed memory.
A re-parent (AddChild of an element that has a parent) is not a removal.

A wrapper holds a reference to what it wraps ([SECURITY_RUN_1];
magic_sandbox and src/lua_bindings/misc_urho3d.cpp's hold_ref), so an object
the engine lets go of -- a cloned RenderPath with its viewport -- lives as
long as a wrapper of it does. What is a place in another object's vector is
not wrapped that way: a RenderPathCommand dies when its path's Append or
Load moves the vector (GetCommand again), and a Bone is read out as a table
{name, parentIndex, animated, node}. A Variant's Ptr is handed back only
as what the object is, or a base of it.

The client sends Urho3D's ExitRequested event when it is shutting down, for
any reason and not only a closed window, so that a module can close what it
opened: the Luanti client tells the server it is leaving there. It arrives
before anything is torn down; a module that is already gone gets nothing.

Additions to regular Urho3D:

SubscribeToEvent(event_name, callback)
- callback: function(event_type: string, event_data: VariantMap)
SubscribeToEvent(object, event_name, callback)
- callback: function(object, event_type: string, event_data: VariantMap)
- Callback can be a function, unlike in plain Urho3D where it must be a global
  function name. Global events are multiplexed: several subscribers to one
  event all get it.
- Return value: name of the generated global callback, for
  UnsubscribeFromEvent(event_name, callback_name).

UnsubscribeFromEvent(event_name, callback)
- callback: the name SubscribeToEvent returned, a function, or the name of a
  global function in the caller's own sandbox environment -- the same three
  things the subscribe takes. A subscription is stored under a generated name,
  so a handler unsubscribed by the name its own file calls it by used to match
  nothing and go on firing over a screen it had already removed.

buildat.parse_json(text) -> value, or nil and why not
- JSON to plain Lua: objects become tables keyed by their names, arrays
  become lists from 1, and strings, numbers and booleans are themselves. What
  an app fetches with network.http_get is what this is for.
- A JSON null becomes nil, so an array with nulls in it has holes and # stops
  at the first one. A document nests 64 deep at most, and 8 MB is refused.
- Urho3D's own JSONFile and JSONValue are not on the whitelist: their getters
  answer references into the parent document, which dangle when it is
  collected. This copies instead, so nothing the sandbox holds is a C++
  object.

A mesh built from Lua: VertexBuffer, IndexBuffer, Geometry, Model
- The whole mesh at once, as bytes, where CustomGeometry beside it defines a
  vertex at a time:

    local vb = magic.VertexBuffer:new()
    vb:SetSize(n, magic.MASK_POSITION + magic.MASK_NORMAL, false)
    vb:SetData(buffer)          -- a VectorBuffer of n vertices
    local ib = magic.IndexBuffer:new()
    ib:SetSize(count, false)    -- false: 16-bit indices, up to 65536 vertices
    ib:SetData(index_buffer)
    local geom = magic.Geometry:new()
    geom:SetNumVertexBuffers(1); geom:SetVertexBuffer(0, vb)
    geom:SetIndexBuffer(ib)
    geom:SetDrawRange(magic.TRIANGLE_LIST, 0, count)
    local model = magic.Model:new()
    model:SetNumGeometries(1); model:SetGeometry(0, 0, geom)
    model:SetBoundingBox(magic.BoundingBox(lo, hi))
    node:CreateComponent("StaticModel").model = model

- The elements go in Urho3D's own order -- position, normal, colour,
  texcoord -- and the mask says which are there. A model with no bounding box
  is culled away and never drawn, which looks like the mesh not working.
- The lifetimes hold themselves: a Geometry keeps its buffers, a Model its
  geometries and a StaticModel the Model, all by reference count.

DebugRenderer, through scene:CreateComponent("DebugRenderer")
- An app's own debug geometry: AddLine, AddTriangle, AddCross, AddCircle,
  AddSphere, AddBoundingBox and AddNode, each taking a Color and an optional
  depth test. What it is given is drawn by renderer:DrawDebugGeometry([depth])
  and then forgotten, so nothing survives the frame it was added in. SetView
  says which camera it is drawn for, which the renderer does itself for the
  viewport it draws.

Cursor:DefineShape(shape, image, rect, hot_spot)
- An app's own cursor art, for a Cursor element of its own. The shape is
  Urho3D's name for one ("Normal", "ResizeVertical", ...).
- The image has to come out of the resource cache: Urho3D hands it to a
  SharedPtr, which would free an image the sandbox built from under the
  collector. An image with no name is refused for that reason.

LineEdit.multiLine, UIElement:IsMultiLine()
- The fork's multi-line LineEdit (doc/magic.txt): Enter breaks the line,
  Ctrl+Enter sends TextFinished, the text wraps. ui_utils' keyboard_page
  asks IsMultiLine() of the focus and leaves Up and Down to such a field.
- Every field has the common editor keys ([TEXT_KEYS], doc/magic.txt):
  Ctrl+A, Ctrl+Left/Right by word, Alt+Backspace and Ctrl+Backspace back a
  word, Ctrl+Delete forward, a double-click a word, a triple-click all (in a
  multi-line field the line).

magic.ui.focusElement, Text.selectionStart, Text.selectionLength
- The focus reads as what it is when its class is whitelisted, as GetChild's
  children do: a field as a LineEdit, with its cursorPosition and
  textElement. A Text's selection is read-only; uistack's scan prints a
  focused field's "cursor N selection S+L" ([TEXT_KEYS]).

XMLFile:GetRoot([name]) -> XMLElement, XMLFile:ToString([indentation])
- An app's own XML, read: the file comes out of the resource cache like any
  other media (magic.cache:GetResource("XMLFile", "mygame/data.xml")), and the
  element walks it -- IsNull/NotNull, GetName, GetValue, HasChild,
  GetChild([name]), GetNext([name]), GetParent, GetFile, HasAttribute,
  GetNumAttributes, GetAttribute(name), GetBool/GetInt/GetUInt/GetFloat/
  GetDouble(name), and GetVector2/GetVector3/GetColor/GetIntVector2(name).
- The reading half only. The setters build a document with nowhere to go,
  XMLFile:Save() taking a path on the user's disk, and FromString() would
  rewrite a file the cache may be handing to somebody else.

magic.render_scene_to_texture(scene, camera_node, w, h) -> Texture2D
- A scene drawn into a texture instead of into the window. What wants it is a
  thumbnail: a voxel volume or a model seen on its own, on a button, which is
  what the structures menu in apps/demo_aggregate wears.
- The camera node needs a Camera component. The texture keeps updating every
  frame, so geometry built asynchronously -- set_voxel_geometry() -- appears
  when it arrives without anything asking for another update.
- One function rather than RenderSurface and its update modes, because a
  thumbnail is all anyone has needed. Neither the texture nor its viewport is
  ever freed; the upgrade path, for a live mirror or a portal, is to expose
  RenderSurface properly.
- The scene is drawn with its own viewport and no postprocessing, so a scene
  lit for the main viewport's HDR tonemapping comes out blown out. Light a
  thumbnail scene for the low dynamic range it is.

magic.set_preferred_viewports({viewport, ...})
- The viewports the user's graphics preferences are applied to, as against the
  raw renderer:SetViewport() ones, which are drawn the way the app says and
  nothing else. That is what "preferred" means throughout this API: it honours
  what the user asked for.
- Use it instead of renderer:SetViewport(). The engine draws the scene at the
  user's render_scale, under a UI that stays at native resolution, and the
  viewport stays the app's own -- replacing renderPath afterwards, which most
  apps do, still works, and so does HDR. renderer:GetViewport(0) answers with
  the app's preferred viewport when the renderer holds none (it is on a
  texture then), so a render path set through it reaches the picture.
- The whole list at once, because Urho3D needs both a viewport per slot and a
  count. An empty table is teardown: nothing is left on the screen.

      magic.set_preferred_viewports({viewport})            -- one view
      magic.set_preferred_viewports({vp_top, vp_bottom})   -- two
      magic.set_preferred_viewports({})                    -- teardown

- Declarative: this is what is on the screen now. An app that moves a viewport
  rect -- apps/demo_bomber_drone splits the window in half -- calls it again after
  setting the new rects, and the rects it reads are in window pixels whatever
  the scale is, so nothing about screen-to-world maths or picking changes.
- An app that does not call this is drawn at native resolution and keeps
  working. The preference is a preference: the client owns how much the frame
  costs, the app owns what is in it. That is the deal, not a gap to be closed
  later.

Engine settings
---------------
What the user sets once and every app honours: how much the frame costs and
how loud it is, never what the art is. Kept in user/settings.json, and
overridden for one run by -o (see README.md).

    render_scale    3D viewports drawn at this fraction of the window size;
                    the UI stays at native resolution. 1.0 is a bypass;
                    "auto", the default, is the client's choice (see
                    get_render_scale)
    vsync           present synchronised to the display
    max_fps         frame limiter; 0 is unlimited
    multisampling   MSAA samples: 1, 2, 4, 8 or 16
    sound_volume_db decibels below full, 0 to -30 and off under it
    sound_mute      that gain forced to zero
    ui_size         the UI scale, 0.5 to 3, or "auto", the default, which
                    follows the window (see get_ui_size); -u for a run
                    wins over it
    default_username the name an app offers when it asks for one, "User"
                    by default: 1 to 20 letters, digits, _ and -

render_scale is cooperative: it reaches an app's viewports only through
set_preferred_viewports(), because a viewport belongs to the app that made
it. The sound pair is enforced, because Urho3D already multiplies every sound
type's gain by the "Master" one -- which is why Audio:SetMasterGain("Master")
is refused in the sandbox. Apps have "Effect", "Music", "Ambient" and
"Voice", and their own mixing multiplies under the user's setting.

Shadow quality, texture and material quality, filtering, FOV and draw distance
are deliberately not here: each one changes what the app looks like or what a
player can see, and the app is the one that should say.

The launch menu has a page of them, in extensions/launch_menu/preferences.lua. It
is a page of widgets over buildat.get_preference() and set_preference() and
knows nothing about the file, which is why the C++ side is the authority for
them in the first place.

blip
----
sfxr's sound effects, made with buildat.synth ([BLIP]); its launch tile is a
designer for them. A sound is a "blip1:..." string, a table of the
parameters by name ({wave = "square", base_freq = 0.3, ...}, the missing
ones at their defaults), or the string plus a partial table that overrides
it ({"blip1:...", volume = 0.2}). blip1 is frozen: a sound sounds the same
in every later blip.
blip.play(sound [, opts]) -> SoundSource
- Made and played, not kept. opts: {gain, panning, type, node}, type the
  SoundSource's sound type ("Effect"), node one of the caller's to play on.
blip.play_cached(sound [, opts]) -> SoundSource
- Made once into a Sound (at most 64 kept), played again from it.
blip.stream([opts]) -> mixer
- A mixer on one stream, opts as play's plus rate (44100, or 22050 for a
  cheaper stream). mixer:add(sound [, at, gain]) mixes the sound in, at
  seconds after what is queued; mixer:stop().
blip.wav(sound) -> the bytes of a 16-bit mono 44100 Hz WAV file
blip.params(sound) -> the parameter table; blip.pack(p) -> "blip1:..."
blip.preset(name, seed) -> p, name one of sfxr's generators (pickup,
  laser, explosion, powerup, hit, jump, blip)
blip.self_check() -> true, or false and the presets that moved: each
  generator's sound at seed 1 hashed against blip1's committed hashes
blip.gen, blip.mix
- extensions/blip/blip_gen.lua and blip_mix.lua, the generator and the
  mixer: plain Lua that an app may copy into its client_lua instead
  (the designer's "Save the files"), and so not follow blip's versions.

replicate
---------
Interface to server->client synchronized (replicated) scenes.

Note:
	There is a gotcha in scene replication: Resources are replicated by resource
	name, meaning that resources like Materials and Models created or edited on
	the server will not be replicated on the client.

	If you wish to create or edit resources used by the replicated scene, you
	can use urho3d.sub_sync_node_added() to listen to node additions and name or
	otherwise augment your nodes in such a way that you can generate or set
	resources to each node that requires it.

	The sandbox wrapper adds the client-side components to the node using
	urho3d.LOCAL by default, avoiding the problems of accidentally using
	urho3d.REPLICATED on the client.

	Make sure to not set anything to that resource of the node on the server
	side, because then you will get unpredictable fighting between the one set
	on server-side and client-side.

	Example: apps/sample_server_entities/main/client_lua/init.lua

	The client makes only the component types that hold the scene, draw,
	collide or sound (src/client/state.cpp, `replicable`): Octree,
	PhysicsWorld, Zone, Light, Camera, the models and geometries, the
	billboards, particles, trails, decals, Text3D, Skybox, Terrain, the
	physics bodies, shapes and constraints, the sound sources and
	SmoothedTransform. Anything else -- a LuaScriptInstance would run
	outside the sandbox -- is logged and ends the node there.

replicate.main_scene
- Main replicated scene instance. To show it on screen, add a camera and a
  viewport. Add your local stuff to this as needed.
- You don't have to use this if you wish to synchronize your scene in a custom
  way.
- CreateNode and CreateComponent uses urho3d.LOCAL by default unlike native
  Urho3D. With urho3d.REPLICATED (native default) they will end up in the
  synchronized ID space and will be overridden by data coming from the server.
- A property whose Urho3D type is a **const reference** -- `const Vector3&`,
  `const Vector2&` -- has a getter and **no setter**: tolua++ generates
  `tolua_variable("minDirection", getter, NULL)` for it. Assigning such a
  property writes nowhere and reads back what was assigned, so it looks like
  it worked. Where it matters the sandbox exposes the class's own setter
  function instead: ParticleEffect has SetMinDirection, SetMaxDirection,
  SetMinParticleSize, SetMaxParticleSize, SetConstantForce and
  SetEmitterSize, and its matching properties are read-only. The other
  const-reference properties in these bindings are things nobody assigns
  (bounding boxes, frustums, world transforms); Zone's ambientColor and the
  rest of the vector properties do have setters.
- An Urho3D object made in Lua -- a Material, a ParticleEffect -- belongs to
  Lua and is destroyed when the last Lua reference to it goes, whatever the
  engine still holds it in. Keep a reference for as long as the component
  using it lives. An emitter whose effect has been collected reads freed
  memory, which on this machine came out as Urho3D's defaults: particles
  scattered in random directions at the default size.
- Node:Clone([mode]) is there as well, also LOCAL by default: a copy of the
  node and its components in the same parent, made inside the engine. What
  wants it is geometry that costs a sandbox call per vertex to build and is
  wanted more than once. Urho3D copies a component through its attributes,
  so a material made in Lua -- which has no resource name to be referred to
  -- is not copied and has to be set on the copy.

network
-------
TCP and UDP sockets, with the user in the loop: the first connection or
datagram to an address in a week needs the user to accept the address and give
it a description. Answers live in user/network_addresses.csv, one row per
asking server and address ([CONSENT_PER_SERVER]): a server's scripts ask as
their origin (local:<app> for a server this client started, its address
otherwise) and the client's own extensions as "", so what the user gave one
server's scripts another's ask for again. The dialog names who asks, and
declines by itself when a script changes any of its elements or pushes
something over it.

The socket objects are LuaSocket's, as far as the safety layer allows. What
differs from LuaSocket:
- Opening a socket takes a callback, because the user has to answer the dialog
  first, and the address comes with it: there is no socket.tcp() / socket.udp()
  followed by connect() or setpeername()
- A socket only talks to the one address the user accepted. Listening sockets
  and unconnected UDP do not exist here; setpeername(), setsockname() and
  sendto() to another address return nil and a message
- The sockets are always non-blocking, as with LuaSocket's settimeout(0);
  settimeout() accepts 0 and warns about anything else
- socket.select(), socket.sleep(), socket.dns and socket.bind() are not
  provided. Poll the sockets from an Update handler instead
- socket:address() is not LuaSocket's; it is the address as the user accepted
  it, for showing in a UI

tcp_connect(host: string, port: number, cb: function [, options])
udp_connect(host: string, port: number, cb: function [, options])
- cb(socket, error) is called once the user has answered; socket is nil if the
  connection was not made or the user declined. options.description fills the
  permission dialog's description field, editable, the answer still the
  user's ([NET_DESC]); http_get takes the same. A call without one logs
  "no description from the caller for <uri>" when the dialog asks. Return
  in the field accepts, as Accept does.
http_get(url, cb [, options])
http_post(url, json_body, cb [, options])
- cb(body) or cb(nil, error), fetched on a thread and read back on Update.
  http and https only; the consent is for the url's host and port, and a
  redirect (a GET's, 8 at most) goes through the same consent for its own
  host rather than being followed by libcurl.
known_addresses() -> {{uri, description, created, last_attempt, accepted},
  ...}
set_address_name(uri, name)
- The addresses this client has used, the last used first and each once,
  and the player name last used on one, kept on its rows for the next
  connect screen ([BOX_PLAYTEST_2] 4). The user's address book: launch UIs
  and the client's own extensions have these two, and the network a
  server's chunks require does not.
unseen_counts(cb)
- cb(address, count) for each Buildat server joined (tcp) that this
  client keeps a login for and that answers POST /unseen with that login
  (a Hearth: its notifications waiting). Native only; withheld from a
  server's chunks like the two above.
parse_json(text) -> table, or nil and error
write_json(value [, styled]) -> text, or nil and why not

gettime() -> seconds

Socket methods, as in LuaSocket:
- send(data [, i [, j]]) -> index of the last byte sent, or nil, error
  [, index of the last byte sent]
- TCP receive([pattern [, prefix]]) -> data, or nil, error [, partial data].
  Pattern is a number of bytes, "*a" until the peer closes the connection, or
  "*l" one line (the default). Error is "timeout" when what was asked for has
  not arrived yet, or "closed".
- UDP receive([size]) -> one datagram, truncated to size if given
- UDP receivefrom([size]) -> data, ip, port
- getpeername() -> ip, port
- getsockname() -> ip, port
- settimeout(0)
- close()

See extensions/network_test for a working example:
  $ bin/buildat -m network_test

magic_sandbox

Unsafe interfaces of built-in extensions
========================================

urho3d
------
The unsafe interface consists of the namespace tables "safe" and "unsafe". Use
the safe interface unless the unsafe one is specifically needed:
  require("buildat/core/urho3d").safe

This enforces interoperability between modules and extensions.

If you get an error like this:
  'Disallowed type: "userdata"; Allowed types: ...'
You probably are giving a non-sandboxed object to an interface that requires
sandboxed ones.

An actual unsafe Magic interface is available in:
  require("buildat/core/urho3d").unsafe

DO NOT USE the unsafe version of urho3d unless specifically needed. All
interfacing with other extensions and module code has to be done using the
sandboxed version in order to make interfacing possible between all of them.

The unsafe version of the urho3d extension actually just wraps to the global
environment, except for the additions to the API documented here.

Note that due to technical reasons Magic's non-sandboxed API is currently
always globally defined in the extension environment, but this will not be
supported in the future.

Additions to regular Urho3D:

SubscribeToEvent(event_name, callback)
- callback: function(event_type: string, event_data: VariantMap)
SubscribeToEvent(object, event_name, callback)
- callback: function(object, event_type: string, event_data: VariantMap)
- Callback can be a function, unlike in plain Urho3D where it must be a global
  function name.
- Return value: Name of the generated global callback which can be unusbscbribed
  from Urho3D via UnsubscribeFromEvent(event_name, callback_name).


Miscellaneous
=============

You can create a client-side voxel registry like this:

local voxel_reg = buildat.createVoxelRegistry()
local atlas_reg = buildat.createAtlasRegistry()
-- A format first: there is no default (see set_format below)
voxel_reg:set_format("blocks")
do
	-- Air says it is air: nothing occupies it, so the sky passes it and
	-- a merge writes into it. A voxel with empty edges and nothing to draw
	-- that says neither fully_empty nor transmits_light is refused.
	local air = buildat.VoxelDefinition()
	air.name.block_name = "air"
	air.face_draw_type = buildat.VoxelDefinition.FACEDRAWTYPE_NEVER
	air.edge_material_id = buildat.VoxelDefinition.EDGEMATERIALID_EMPTY
	air.fully_empty = true
	voxel_reg:add_voxel(air) -- id 1

	local vdef = buildat.VoxelDefinition()
	vdef.name.block_name = "rock"
	local textures = {}
	for i = 1, 6 do
		local seg = buildat.AtlasSegmentDefinition()
		seg.resource_name = "main/rock.png"
		seg.total_segments = magic.IntVector2(1, 1)
		seg.select_segment = magic.IntVector2(0, 0)
		table.insert(textures, seg)
	end
	vdef.textures = textures
	vdef.edge_material_id = buildat.VoxelDefinition.EDGEMATERIALID_GROUND
	vdef.physically_solid = true
	voxel_reg:add_voxel(vdef) -- id 2
end

vdef.tile_turns is six quarter turns, one per face, of the texture inside its
own face: {0, 0, 0, 0, 0, 0} for a voxel that does not turn one. What wants it
is a voxel that faces a direction -- the top of a turned cube wears the same
texture as the top of one that is not turned, turned with the voxel -- so the
turn belongs to the face rather than to the atlas segment, which is shared.
A shape's quads carry their own texture coordinates and are not affected.

vdef.uv_scale is how many voxels one repeat of the texture spans across a
face ([WORLD_UV]): 1 is one repeat per voxel, and at more than 1 the mesher
takes the phase of the repeat from where the voxel is in the world, so a
neighbour continues the sequence rather than starting again. vdef.uv_scale_v
is the same upwards, and nought means "the same as uv_scale" -- which is the
square case and every definition written before it. A frieze eight voxels
across and one tall wants uv_scale = 8 and uv_scale_v = 1; with one number
for both axes a slab's edge showed one eighth of the texture's height, chosen
by where the slab sat in the world.

vdef.variants says what a voxel's param does to how it is drawn, for a
format that binds one. It is an array of variants, and a variant claims the
param values it applies to:

  vdef.variants = {
      -- A cube that faces a direction: the same six textures in another
      -- order, each turned inside its own face
      {tile_order = {1, 2, 3, 4, 5, 0}, tile_turns = {0, 0, 1, 3, 2, 0},
              params = {2, 6, 10}},
      -- Light tinted blue, and a liquid standing a quarter of the way up
      {shape = {}, color = 0x336699, liquid_top = 0.25, params = {1}},
  }

- params is the list of param values that pick this variant, 0...255, and is
  the one field that is not optional: a variant nothing reaches is a mistake.
  A param value no variant claims is drawn as if the param changed nothing.
- tile_order[f] is which of the definition's own six textures face f wears,
  0...5. A variant carries no textures of its own: a turned cube wears the
  same ones in a different order, which is what keeps a voxel that faces
  twenty-four ways from needing twenty-four voxel types.
- shape replaces the definition's own quads, and is empty for a variant that
  keeps them. tile_order and tile_turns are for cube faces; a shape's quads
  carry their own texture coordinates, as always.
- color is multiplied into the vertex colour, 0xRRGGBB. The vertex colour is
  light, so this tints the light the voxel gets and not its texture: a glow,
  coloured shade. It is not a palette, which would show in shade and vanish
  in sunlight; a palette over a texture is the tint modifier, a field the
  format binds, picking between the two ends of the definition's tint_ramp
  (see set_format below and src/interface/voxel.h).
- liquid_top is where a liquid's surface stands in the voxel, which is what
  Luanti's flowing liquids put in param2. The corner heights that make a
  surface continuous read the neighbours' own params too.
- Only a param up to 8 bits wide is looked up this way. A wider one is
  storage for the app to read itself.

voxel_reg:set_format{...} says how the app cuts up a voxel's 32 bits. There
is no default: add_voxel() is an error until a format is set. Say it before
the first voxel is added: everything already stored, and every volume on its
way anywhere, is bits under the format.

voxel_reg:set_format("blocks") picks one of the named layouts instead, which
doc/server_api.txt lists ("blocks", "many_ids", "painted", "surfaces",
"luanti", and "buildat_legacy_06", the cut buildat had before formats: the
type id in bits 0...20 and two 4-bit light levels in 24...31). A name that
is none of them is an error.

  voxel_reg:set_format{
      plane_bits = 32,                    -- the app's own plane's width
      id = {shift = 0, width = 16},       -- indexes the registry
      light_sky = {shift = 16, width = 4},
      light_lamp = {shift = 20, width = 4},
      param = {shift = 24, width = 8},    -- a definition's own rule reads it
      color = nil,                        -- 0xRRGGBB, width 24 or 32
      -- and the modifiers, none of them bound by default:
      tint = nil, wetness = nil, grain = nil, gloss = nil,
      speckle = nil, emission = nil,      -- surface, at most four at once
      sag_top = nil, sag_bottom = nil,    -- geometry
      planes = {                          -- planes after the app's own
          {name = "mymod:heat", bits = 8},
      },
  }

- Those five are the roles the engine understands. A role left out is not
  bound, which is not the same as one that is always zero: a world with no
  light bound is not dark, it is one where nothing asks about light. Bits no
  role covers are the app's own.
- Bind the light the world actually fills and no more. light_lamp is for a
  world that works out the light a voxel gets from something other than the
  sky and stores it per voxel, which is what a Luanti server does; an app
  whose lamps are lights in the scene wants only light_sky, and the shader
  lights the geometry from the lamps.
- id is what the registry is indexed by, at most 21 bits wide. With no id
  bound there is one voxel type, which is what an app whose voxels are
  colours rather than types wants.
- param is handed to the voxel's definition, which is what says what it
  means: which way the voxel faces, how high a liquid stands in it, which
  of its variants it is drawn as.
- color is 0xRRGGBB in the low 24 bits of a field 24 or 32 bits wide, and is
  multiplied into the vertex colour. That colour is light rather than albedo,
  so it tints the light a voxel receives and not its texture: right for a
  app whose voxels are unlit colour, wrong for a palette over a texture.
- The modifiers say how much of something a voxel has, where a role says
  what it is. Each is normalised against its own field's width, so a 4-bit
  field and an 8-bit one both run 0...1 and an app can widen one without
  touching its shader.
- The surface modifiers reach the shader as four numbers in the vertex
  tangent and nowhere else; the engine promises the four and their order and
  the app's shader decides what they look like. The order is tint, wetness,
  grain, gloss, speckle, emission, with the bound ones packed towards x --
  fixed rather than the order they were written, so that two worlds binding
  the same roles hand their shaders the same thing. At most four may be
  bound; a fifth is refused.
- tint is the one that is a colour rather than a scalar: it picks a colour
  out of vdef.tint_ramp = {0xRRGGBB, 0xRRGGBB}, the first end at 0 and the
  second at full, and its slot carries that colour packed 5-6-5 instead of a
  number between 0 and 1. A definition that leaves both ends white is not
  tinted whatever the field says. It is an albedo tint and the shader is
  what applies it: the vertex colour is light, and a tint of the light shows
  in shade and vanishes in sunlight, which is not what tinting a material
  means.
- sag_top and sag_bottom move a voxel's top and bottom faces into it, by up
  to vdef.sag_extent voxels. The mesher averages the sag of the voxels that
  meet at each corner, so a sagging surface runs continuously instead of
  stepping; what the sag means -- a liquid's level, a floor giving under a
  load, shallow snow -- is the app's.
- A voxel's bits are stored **a plane at a time**: a plane is one array over
  a chunk holding the same bits of every voxel in it, so a world's voxels
  are several arrays rather than one array of words. A format has one
  32-bit plane unless it says otherwise, which is what every app here has
  and is the same bits in the same order as before planes existed.
- What a second plane is for: a field a simulation sweeps, which it then
  reads a byte per voxel of instead of four; a field a module keeps without
  asking the app for room in a word it has already spent; and a mixture
  world, where the number of fields is the number of materials. A plane
  nothing has written costs a chunk nothing at all.
- A field says which plane it is in: {plane = 1, shift = 0, width = 4}.
  plane defaults to 0, the app's own.
- Reading one: volume:get_plane_at(plane, x, y, z) and its setter, and
  voxelworld.get_static_voxel_plane(p, plane) on the client. Both hand back a
  plain number, because a plane other than the first holds the app's own
  bits and none of the engine's roles. get_voxel_at() and get_static_voxel()
  are the first plane, as they always were. Each plane is 8, 16 or 32 bits, the
  first has no name and the rest must have one, and there are at most eight.
- The fields may not overlap and may not reach past the word. set_format()
  says which rule was broken.
- voxel_reg:dump_format() writes the format out, for a log line.

voxel_reg:set_look_rules{...} says how a voxel's *definition* is found, for a
world whose voxels have no type id at all. The default, and what every app
in this tree does, is the id role of the format: a shift, a mask and an
index. Rules are the other way.

  voxel_reg:set_look_rules{
      fallback = 1,                      -- what no rule claims
      rules = {
          {result = 2, when = {{field = "wetness", lo = 8}}},
          {result = 3, when = {
              {field = {shift = 28, width = 2}, lo = 2},
              {field = "gloss", hi = 3},
          }},
          {result = 4},                  -- everything left
      },
  }

- An ordered list; the first rule all of whose clauses hold says which
  definition the voxel wears. A rule with no `when` claims everything left,
  so nothing after it is reachable and set_look_rules() says so.
- A clause is a field and a range, both ends included. lo defaults to 0 and
  hi to the field's whole range, so a clause with one of them is "at least"
  or "at most". field is a role name or a table {shift = ..., width = ...}
  for a field of the app's own that no role covers.
- The definition is still where every property lives -- what is drawn,
  whether the physics collides with it, whether light passes. A selector
  only changes how the definition is found, so nothing that asks a question
  of a voxel has to know which kind is in use. A world wanting a finer
  distinction in one property than another writes the rules that make it
  and points them at definitions that differ in that property alone.
- Unlike the format this may be set at any time, and a world that changes it
  has to have everything meshed again. What it may not do is point at a
  definition the registry does not have.
- The id role, where it is bound, still says whether a voxel has been
  generated at all -- id 0 is "nothing has got here yet" whatever the rules
  make of the rest of the word.
- It travels with the registry, as the format does. apps/sample_material_wall is
  a world that uses it: two rules over two fields, and no voxel id stored
  anywhere.
- The format travels with the registry, so a client that deserializes one
  gets the world's cut along with its definitions.

atlas_reg:set_surface_maps(false) says the app's voxel shader samples the
diffuse atlas and nothing else. An atlas then carries neither the normal map
nor the surface map derived from its segments' pixels, which is two thirds of
what adding a texture to an atlas costs and two thirds of its memory. Say it
before the first segment goes in; a later change only reaches atlases created
after it.


Voxel data
----------
buildat.pack_voxel_volume(args) -> string
- Packed samples in, a serialized volume out. What comes out is what
  set_voxel_geometry() and buildat.deserialize_volume() take.
- One strided box copy per source, with an optional value mapping. Somebody
  else's voxel format goes in without a Lua call per voxel: a Luanti mapblock
  and the one-voxel border it needs from its six neighbours is seven sources
  and two fields in one call.

  buildat.pack_voxel_volume{
      region = {x0, y0, z0, x1, y1, z1}, -- inclusive corners
      registry = <VoxelRegistry>,        -- optional; whose format applies
      fill = 0,                          -- raw voxel value the rest gets
      sources = {
          {
              data = <string>,           -- the packed samples
              format = "u16be",          -- u8|u16be|u16le|u32be|u32le
              source_size = {16, 16, 16},-- the sample array, in x, y, z
              from = {0, 0, 0},          -- the box to copy, in samples
              size = {16, 16, 16},       -- default: the rest of the source
              at = {0, 0, 0},            -- where it lands, in region coords
              order = "xyz",             -- which axis runs fastest, first
              shift = 0,                 -- sample = (sample >> shift) & mask
              mask = 0xffff,             -- default: all of the format's bits
              map = <string|table|nil>,  -- key -> value written
              map_default = nil,         -- for keys the map does not have
              map_id = nil,              -- compile this map once; see below
              map_version = nil,         -- bump when the map changes
              field = "id",              -- a role of the voxel format
              second = {                 -- optional; nil for one array
                  data = <string>,       -- as long as the first array
                  format = "u8",
                  shift = 0,             -- (sample >> shift) & mask
                  mask = 0xff,
                  scale = 65536,         -- key = first + second * scale
              },
      },
  }

- field says which part of a voxel a source writes, by naming a role of the
  voxel format rather than a bit range: "id", "skylight", "lamplight",
  "light" (both light channels in one write, the sky light in the low bits),
  "param", "color", or "raw" for the whole word. Where a role actually is
  depends on the format, which comes from args.registry, and a call without
  one is an error. Other bits are left alone, so ids and light are two
  sources over the same box.
- A field naming a role the format does not bind is an error, as is "light"
  in a format whose two light channels are not adjacent.
- map is a table indexed by the key, or a string with one byte per key. A key
  the map does not mention gets map_default, and with no map_default the voxel
  is left as it was. Keys too far apart to be an array are held as a hash, so
  a sparse table of large keys costs what it holds rather than what it spans.
- map_id names a map so that it is compiled once instead of once per source.
  A map of a few thousand keys costs more to compile than the box copy itself,
  and a voxel world hands the same map to every source of every block. The
  ids are the caller's to pick, small integers; map_version is what says the
  map has changed, so bump it on every write to the table. A source with no
  map_id compiles its map every time, which is what a one-off wants.
- second is a second sample array read in lockstep with the first, at the same
  index: the key looked up is first + second * scale. What wanted this is
  Luanti's param2, which decides a voxel's colour or which way it faces, so
  what a voxel looks like is a pair of samples rather than one -- one voxel id
  per (type, param2) pair that actually turns up.
- A source box that hangs over the edge of the region is clipped, which is what
  a border slice from a neighbour that has not arrived yet needs.

buildat.compose_image(args) -> width, height
- Raster operations over an RGBA canvas, saved as a PNG. What wanted this is
  Luanti's texture modifiers ("dirt.png^grass.png", "[colorize:#ff0000:128",
  "[combine:32x32:0,0=a.png"), which are a small language over these
  operations; the language itself belongs in the app's own code.

  buildat.compose_image{
      size = {16, 16},        -- the canvas; default: the first blit's
      write = "<path>",       -- where the PNG goes; under the cache path only
      ops = {
          {op = "blit", src = "a.png",   -- a resource name
              src_data = nil,            -- or the bytes of a file instead
              from = {0, 0, 16, 16},     -- default: the whole source
              at = {0, 0},
              size = {16, 16},           -- scales, nearest neighbour
              fill = false,              -- or: over the whole canvas
              clip = {0, 0.5, 1, 1},     -- fractions of the canvas
              blend = "over"},           -- over|set|and|multiply|screen
          {op = "fill", color = {r, g, b, a}, at =, size =, blend =},
          {op = "multiply", color = {r, g, b, a}},   -- per channel, 255 = 1
          {op = "colorize", color = {r, g, b, a}, ratio = 0..255},
          {op = "hsl", hue = 0, saturation = 0, lightness = 0},
          {op = "alpha", value = 255},   -- set the whole alpha channel
          {op = "chromakey", color = {r, g, b}},  -- that colour turns clear
          {op = "transform", transform = 0..7},  -- the square's symmetries
          {op = "resize", size = {w, h}},
          {op = "crop", from = {x, y, w, h}, size = {w, h}},
          {op = "crop", grid = {cols, rows}, cell = {x, y}},
          {op = "shear", src = "a.png",  -- onto a parallelogram
              at = {x, y},               -- where the source's 0,0 goes
              u = {dx, dy},              -- and its right edge
              v = {dx, dy},              -- and its bottom edge
              blend = "over"},
      },
  }

- With no size, the first blit makes the canvas as big as it needs, which is
  what a chain of overlays over a base image wants.
- A blit's source is a resource name or, with src_data, the bytes of an image
  file the caller already has. What wants the second is Luanti's "[png:",
  which carries a whole PNG base64-encoded in the expression itself.
- There is no way to keep an intermediate image: a nested expression is one
  call per level with the inner results referenced by the name they were
  written under, which doubles as a cache between runs.
- transform is the eight symmetries of a square: 0 identity, 1...3 rotations
  by 90 degrees counterclockwise, 4 flip x, 5...7 that flip and then those
  rotations. An odd one swaps the width and the height.
- crop with a grid cuts the canvas into cols by rows cells and keeps one,
  which is what a sprite sheet or a stack of animation frames is. A zero for
  one side of the grid means "as many as makes the cells square", which is
  how many frames a strip holds without anybody having to count them.
- clip is a rectangle of the canvas, in fractions of it, outside which a blit
  writes nothing. It is fractions rather than pixels because what wants it --
  an overlay stretched over the whole canvas of which only a part is drawn --
  is written by someone who does not know how big the canvas is.
- chromakey makes every pixel of exactly that colour fully transparent, which
  is what a texture drawn over a solid background and saved without an alpha
  channel needs; the comparison is exact, because such a texture has one
  exact background colour.
- colorize blends towards the colour by ratio and leaves fully transparent
  pixels alone; at ratio 255 it replaces the colour and multiplies the alpha.
- shear puts the source's four corners at at, at+u, at+u+v and at+v: u is
  where its right edge goes and v where its bottom edge goes, so u = {w, 0}
  and v = {0, h} is a plain scaled copy. It is worked out backwards, from
  each destination pixel to the source pixel it holds, so the result has no
  gaps whatever the edges are, and pixel centres decide it, so two
  parallelograms sharing an edge cover the pixels along it once each. What
  wanted this is the little isometric cube an inventory draws a voxel as:
  three tiles, three parallelograms.

buildat.read_image(resource_name) -> width, height, rgba
- The pixels of an image, as one string of four bytes per pixel, row by row.
  What wanted this is a colour palette: an image of a few dozen pixels that a
  app indexes to say what colour something is drawn in.

VoxelDefinition.shape
- A shape of the voxel's own instead of a cube: an array of quads, each
  {tile = 1...6, p = {12 numbers}, uv = {8 numbers}}. The corners are in the
  voxel's own cube of -0.5...0.5 and the texture coordinates in the tile's own
  0...1 with 0,0 at its top left. Empty for a cube, which is what most voxels
  are and the fast path the voxel mesher exists for; a voxel with quads has
  them copied into its chunk's mesh, which costs about what its own faces
  would have -- rather than a scene node per stair.
- Wind a quad's corners so that the right-handed cross product of its first
  two edges points out of the shape; the mesher takes that as the normal too.
  Corner order top left, top right, bottom right, bottom left as the face is
  seen from outside does it.
- VoxelDefinition.shape_double_sided draws the quads from both sides, which a
  shape made of single quads -- a plant, a rail, a sign -- wants and a shape
  made of boxes does not.
- A voxel with a shape usually wants face_draw_type FACEDRAWTYPE_NEVER and
  edge_material_id EDGEMATERIALID_EMPTY too: the cube faces it would
  otherwise have are not what it looks like, and its neighbours should draw
  their faces against it.

volume:serialize() -> string
- The same thing a Volume built one set_voxel_at() at a time can hand to
  set_voxel_geometry(). The slow, flexible path; pack_voxel_volume() is the
  fast one.
